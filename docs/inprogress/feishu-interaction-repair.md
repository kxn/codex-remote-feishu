# 飞书交互整改：保留单聊体验，收敛群展示与发布

> Type: `inprogress`
> Updated: `2026-11-22`
> Summary: 记录已确认的单聊菜单和执行展示恢复、群低频展示、发布能力边界，以及实施拆分和使用流程验收。

本方案根据用户实际使用反馈制定，已获准实施。它修正[产品主文档](../draft/feishu-agent-team-product-design.md)中把私人停止隐式映射为项目暂停等不合理规则；此前把旧菜单和输出规范整体标成历史，不代表可以放弃其交互体验。运行时仍采用持久团队、记忆、原生会话恢复和 outbox，不重新启用旧调度引擎。旧单聊体验的代码对照基线为 `36b1e1e6`。

## 用户应当得到的体验

### 单聊仍然是直接和一位助手工作

普通输入、答复、菜单、执行反馈和文件直接出现在这个私聊里，不自动创建飞书话题。内部会话归属、历史恢复与平台展示分开。普通原生最终答复由系统保证显示，不要求模型主动使用发布工具；显式发送过的同一答复不得重复。

恢复原有菜单分组、适用入口、层级与返回。菜单首页到参数、模型、保存、目录、历史及返回在同一张已确认卡片内完成。主动从平台菜单重新打开可以产生当前位置的新入口；卡片内导航不能默认另发。内容、选项、当前值、成功反馈和错误必须说明实际操作，去掉无助于判断的泛泛说明。保留有用的 Slash 命令，不恢复已取消的 Cron、原生人工接管和历史改写功能。

恢复旧执行展示：排队、开始、同轮过程卡、阶段性正文、计划、文件变化、适用工具活动、压缩状态、停止、失败、原生问题、最终 Markdown／代码／长文／图像与可验证的用量信息。保留 quiet／normal／verbose／chatty 的原有区分，只展示后端实际提供且可对用户公开的事件，不暴露原始敏感工具负载或模型私有推理。复用原渲染与归并能力；每个 token 不进入业务持久日志，最终正文和阶段事实必须可恢复、顺序明确、去重。

私聊的停止只作用于选定私人执行及其原有待派发用户输入，不因看过某个项目扩大到整个项目。停止后新消息可正常处理，无需另按继续；旧轮的自动继续不能借新消息的准入重启。项目暂停／恢复仅在明确的项目操作或实际自然语言指令中使用。菜单不无条件并排放暂停和继续。查看历史／项目不暗中发起工作；明确切换或进入关联讨论才改变后续输入归属。

### 群里呈现团队汇报

主群显示负责人对人的回复、需决定的问题、重要变化和正式交付。话题围绕人关心的工作组织，不按每个内部子任务生成一套执行屏幕。成员内部讨论和任务状态可快速更新，飞书展示按实质变化归并。

默认不广播思考、逐 token 输出、每次工具调用、内部交接、可自行恢复的重试、秒级计时或无变化的心跳。不伪造完成比例，也不将某个成员结束一轮当作任务完成。人可按需查看分工、协作记录和成果；负责人可按人的参与约定多汇报或少汇报，但不得因此绕过频控。

进展默认在稳定卡片内更新。普通状态和完整可读段落同卡最多每 30 秒一次，仅内容有变化才更新；整个群后台展示至少间隔 10 秒，跨 Bot 共用预算。首次重要状态、真人操作、需决定、明确阻塞及正式结果优先，不等待普通进度窗口，仍服从平台硬限额。最终结果到达时取消过期的待发进度，不在完成后回放工作中状态。固定导航与首页不随每次工具事件重写。

这些数值是产品默认值，不是平台额度。飞书[发送消息文档](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/reference/im-v1/message/create?lang=en-US)明确同群 5 QPS 由群内机器人共享。发送、回复、更新、上传分别使用适用限额；应用跨群还需共享应用预算。优先在进入发送队列前保留最新状态，调用层再节流、按平台冷却退避，不能把大量旧进度排队补发。未知发送和未知 PATCH 核对原操作，不盲目重发。

### 内部协作和对人发布分开

| 场景 | 默认能力 |
| --- | --- |
| 私聊助手 | 回复绑定的私人对话；按人的任务发送文件／图片，保留临时分享和正式成果的区分 |
| 群负责人 | 当前项目范围内的对人回复、汇总、问题与正式交付 |
| 普通专家 | 执行任务、内部消息、保存文件和版本、把结果交给负责人；默认不向群发布 |
| 真人直接点名或明确回复的专家 | 对这条真实输入或对应话题作有限回复；不是获得整个群的泛发权限 |
| 明确获交付委派的专家 | 在指定目的地发布获授权的内容类型及成果版本，不要求每次由人重复确认 |
| 后台评审 | 内部交接结果；真人发起的私人评审由系统返回原私聊 |

保存文件、发给同事、发给人是三个不同动作。专家保存草稿和版本不自动把它加入群通知。正文答复同样限制在获授权的会话／话题。普通答复可以包含必要链接；它不自动修改文档访问权、上传附件或登记正式成果。正式交付、资料索引和原件授权仍按清单与资料权限处理。

当前受管进程已不注入旧 `codex_remote_feishu` MCP，旧 Bearer 也被清理；风险来自新 CLI 的发布命令仍对普通专家开放。整改按可信 scope、角色和本轮来源投影工具发现／指令，同时在业务服务和真正发送前校验。隐藏工具或改提示词不能替代授权。

私聊可通过新受管服务提供与旧发文件／图片／视频相容的工具体验；不能恢复旧任意目的地凭据。普通群专家不获得泛用飞书发送 MCP。读取授权资料、评论、图像理解和用户自配研发 MCP 独立保留。直接提及、明确的交付要求和负责人委派必须有实际输入或持久委派依据；模型不能通过传入任意历史 message ID、换幂等键或自报角色获得发布权。角色、任务、Bot 或群变化使旧授权失效；未知结果仍只恢复原发送。

## 实施拆分与所有权

主代理负责产品边界、共享接口、群展示和频控、整合、文档及最终发布。三个便宜子代理各有独立代码范围；共享文件必须先协调，不以缩减用户已确认体验解决实现困难。

| 工作包 | 内容 | 主要代码范围 | 完成证据 |
| --- | --- | --- | --- |
| A 菜单与单聊控制 | 旧分组、单卡导航、设置／目录／历史返回、实际说明、私聊停止与新输入、平台菜单兼容 | `app_work_private*`、preferences／pickers、`workui` 导航、`private_stop`、`feishuapp/team_menu` | SDK 真实回调一路点击，平台消息 ID 不变；查看项目后停止只作用私人执行；新输入可继续 |
| B 单聊执行展示 | 精确原生事件关联、旧过程和最终渲染、详细程度、同轮顺序、去重、暂停／失败／问题反馈；受管私聊媒体能力 | runtime／wrapper 事件、专用私聊输出模块、daemon 接线、相关渲染器 | Codex／Claude 真实协议子进程不调用 publish 仍有正常最终答复；过程同卡、群不泄漏；重放不重复 |
| C 发布权限 | 负责人／专家能力差异、真实直接回复、明确委派、文件版本限制、CLI 发现、服务与出站验证 | `workservice` 发布／授权、grant 存储和领域、CLI 发现、受管媒体授权 | 普通专家直调服务被拒但内部交接正常；真实点名／委派有界成功；伪造来源和撤权失败 |
| D 群展示与调用调度 | 30 秒卡片合并、10 秒群后台预算、跨 Bot 额度、优先级、终态淘汰、避免长期卡错误重放 | project views、publication 调度、store 展示记录、Feishu broker | 多成员并行及故障下实测请求次数／目标／顺序；需人事件优先，过时状态不补发 |
| E 整合复核 | 对照旧体验、完整使用旅程、双状态机、文档单一事实源、发布 | 上述跨组件边界 | 全仓、race、Windows 构建和提交检查；真实平台验证单列，不冒称已验 |

发送地址必须显式区分普通私聊、群主会话和群任务话题；有 ReplyToMessageID 不等于应设置 ReplyInThread。单卡展示归属应覆盖导航流，同时保留业务目标、身份和版本校验，不能简单把所有业务卡改成同一个 key。私聊输出与群汇报不能都由一份群提示词控制。

## 从用户实际操作验收

1. 从平台菜单打开，进入参数→模型→保存→返回→工作目录→选择→历史→返回，检查实际 create／PATCH 请求及同一消息 ID；对转发卡、旧卡、失败更新也检查下一步是否明确。
2. 连续发送普通私聊，普通答复、图片和操作卡留在主会话；显式引用仍指向正确工作。四种详细程度按真实事件展示，最终正文无需 Agent 调用 CLI。长输出、计划、工具、提问、失败、重启和重复事件顺序正确。
3. 私聊查看项目后停止当前私人执行，项目其他成员继续；取消的私人待发消息有记录；新消息能够启动新执行，旧轮不会自行恢复。
4. 群内负责人安排至少两名专家，产生密集内部消息和结果。后台协作照常推进，群无思考流／逐工具更新；多任务状态只产生受控汇总请求，正文按完整内容更新。
5. 专家保存文件并内部交接，群内没有附件或成果通知；负责人选定版本后正常交付。真人点名专家可以收到限定回复，明确文件交付和负责人委派可用；伪造来源、跨任务／群、被撤销授权、改幂等键重复发布均不能绕过。
6. 普通状态排队时插入真人操作／决定／完成，验证优先级和最终状态不会被迟到进度覆盖。限流、网络结果未知、进程恢复及卡片更新失效时不刷屏、不丢正式结果、不影响内部队列。
7. 单个 Bot 服务多个群、多个 Bot 服务同一群，实测共享额度。只检查每个 Bot 自己的测试不算通过。

## 验证边界与实施记录

本方案先落文档再实施。隔离 SQLite、实际 CLI 可执行文件、SDK HTTP／WebSocket 与受控原生子进程用于自动使用旅程验证。真实飞书桌面／移动客户端、真实模型和租户权限另记实际证据；没有实际运行不得写成验收通过。不得为了验证向未指定的真实用户或群发送消息，或擅自部署／重启现有服务。

实施状态：工作包 A 至 E 已接通并经交叉复核。产品主文档、菜单规约与两份 canonical 状态机已同步；以下记录实际验证边界。

命令展示保留可识别的工具、子命令及结构化读写／检索活动；不把不透明的原始参数和潜在凭据带入卡片。公开摘要沿用显示档位，隐藏思考不进入展示。

一次发布委派对应一次对外效果；同一交付可包含多份已许可版本。原 key 重试复用原操作，换 key 不重新发送。普通答复中的链接不能被当作自动授权或交付收据。模型输出不是资料公开的唯一依据。

本轮还修复了旧长文本分段器对“超长单行＋末尾换行”可能无限分割的问题，回归检查完整正文和尾部不丢失。待发查询与同角色进度查询改用 SQLite 过滤和索引，避免每轮逐条读取全部历史消息。

### 部署与验收边界

实现和自动验证均在独立分支与工作区进行。没有重启已有 daemon，没有向真实群发送测试消息。SDK HTTP 及受控原生子进程证据不等于真实模型登录或飞书桌面／移动客户端验收。

宿主 Go 1.24.6 的 VCS 根识别只把 `.git` 目录视为 Git 根，忽略本工作区的 `.git` 文件，继而误选上层不完整目录；`go build -x` 已确认该失败。一次性测试程序与 Windows 交叉编译校验使用 `-buildvcs=false`，不改生产发布脚本，也未修改宿主 Git 目录。

最终检查：`GOMAXPROCS=4 go test -p 2 ./...` 通过；发布、原生运行、存储、入站、业务服务、wrapper 日志及飞书适配器的 race 检查通过；`GOOS=windows GOARCH=amd64 go build -buildvcs=false -p 2 ./cmd/...` 通过。提交前检查通过。除单聊子进程路径外，原有分派／依赖／参与决定的三个群子进程旅程也已复核通过，含并发额度 1 和 2。
