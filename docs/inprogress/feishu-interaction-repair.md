## 本轮纠偏的验收基线

用户多次明确要求单聊基本保留旧体验。实现层的完整性不能替代这一要求，也不能要求用户反复在线上试错才能发现功能取舍。此次进一步核对改版前 `edffb35f` 的实际代码及原产品规则；下表是必须保持的行为，不是重新设计菜单或交互的提案。原始依据包括 [旧单聊产品规则](../general/feishu-product-design.md)及[原鼓掌追加设计](../implemented/feishu-queued-message-applause-shell-command-design.md)。其中旧群调度和用户明确取消的功能不恢复。

| 用户操作 | 必须保持的旧行为 | 本轮已确认的偏移及处理 |
| --- | --- | --- |
| 直接发一句话 | 当前私聊直接续接选定的原生后端会话；答复在主会话中 | 去掉自动创建管理助手和复制私人输入；普通回复不要求工作报告。 |
| 发 `/menu` 或其他适用命令 | 程序直接处理命令，执行忙碌不应把菜单当任务排队 | 沿用此前已修好的独立命令入口；命令不能触发额外模型执行或恢复卡。 |
| 在菜单内进入、选择、返回 | 同一张已确认卡片更新；保持旧分组、返回位置和当前配置说明 | 不因新后端另造导航；已有卡片的未知更新不能通过新发一张卡掩盖。 |
| 打开模型列表 | 已知列表立即可用；刷新不依赖当前执行器健康 | 沿用独立目录缓存，不重新绑定工作执行器。 |
| 修改权限、模型或计划设置 | 旧默认和显式选择保留；普通设置变化不等于丢弃原生历史 | 恢复私人 full access 的旧默认；分清执行参数与账户、提供方等连接身份。 |
| 执行中继续发消息 | 原消息反应表达排队状态；按旧输出档位显示执行过程 | 删除每条待办新增的排队提示卡；恢复反应及公开执行摘要。 |
| 先发图片，再补说明 | 图片先暂存，随同一组说明处理；重复和撤回不制造第二份输入 | 恢复图片暂存、整簇处理、下载失败反馈和停止后的新图片边界。 |
| 给排队说明点赞 | 将文字和绑定图片追加给当前轮次；不得丢图或投到下一轮 | Codex 和 Claude 都接回原有追加能力，只有真实接收证明才确认追加。 |
| 给排队说明鼓掌 | 固定读取文字和附件引用并注入会话；成功只补反应 | 明确撤销本轮错误的“拒绝附图”和“新增命令结果卡”做法。用户文字不被当作任意 shell 命令。 |
| 发消息后立刻点赞或鼓掌 | 原文还在后台处理时不能丢掉操作 | 保存到达时对应的原文和执行目标，等待原文就绪；重放旧回调不能获得新的目标。 |
| 取消确认或停止工作 | 操作到达原来那次执行；保留未处理消息；之后可以继续发消息 | 修复取消的错误目标和未发送误记未知；停止前后输入分别处理，不把私人停止映射成项目暂停。 |
| 遇到真实错误 | 说明具体发生了什么以及当前消息是否保留 | 不使用一律“操作没有完成”的空泛反馈；已显示的核对提示在确认后原卡收口。 |

表中行为必须分别经过真实 SDK 入站、持久输入、原生协议和出站卡片链验证。单元测试或程序内状态变为成功都不能单独称作体验已对齐；测试中的原生响应受控与真人客户端呈现要明确区分。

### Wrapper 复用事实与清理边界

旧 wrapper 的后端适配器、子进程通信、shell 探测、临时文件写入、固定读取命令和原有响应 gate 仍在使用。旧 `shell_command.go` 从上述旧基线到本轮开始的 `e6c77cdf` 没有变化。但是，团队改造已经在 wrapper 外围增加了执行绑定、journal 和 inspection 等较大的包装层；不能把整个改造描述成只换了几个参数。

本轮另查出排队文字和图片引用的 bundle 编码被新 daemon 重复实现。处理原则是提取原有编码供两条入口共用，保留原编码字节与错误语义；不再维护新旧两份格式逻辑。为错误的“命令结果卡”新增、现已没有生产消费者的 stdout/stderr 提取应删除。

原响应 gate 负责同步 RPC 接收、错误和超时；持久回执负责重启后的归属与是否已经写入。两者不能各自消费用户输入。原 turn tracker、进程检查和持久原生记录也必须区分职责，不能仅因都是状态记录就盲目删除其中一份，也不能放任它们分别决定消息是否已处理。私人输入的领取、追加和结算保持单一持久来源，旧 wrapper 能力优先复用。

此次窄清理已用 `edffb35f` 原编码源码作对照：1029 组输入的输出字节、是否有内容和错误结果完全一致。正常原生接收 ACK 曾被新的状态投影误显示为“待核对”，完整流程的严格三次发布断言发现后已纠正，未增加允许卡片数。正文或身份晚到后重投旧 reaction 的真实入口负例也已覆盖，旧逻辑失败、现逻辑通过。

本轮本地检查通过全仓 Go 测试、Windows 构建、相关组件 race、完整 SDK/原生协议图文追加流程和 pre-commit。仓库已有的跨平台测试路径提示仍由 pre-commit 按既定非阻断规则报告；没有将其描述为零告警。随后对照旧入口又修正了应用菜单默认七键、会话历史与列表的区别，以及个人排队消息的分轮处理。直接回复正在执行的原消息时，宿主核验引用归属并只追加这次回复的文字或图片。群项目保留原有批量调度、参与规则和展示预算。

## 用户应当得到的体验

### 单聊仍然是直接和一位助手工作

普通输入、答复、菜单、执行反馈和文件直接出现在这个私聊里，不自动创建飞书话题。内部会话归属、历史恢复与平台展示分开。普通原生最终答复由系统保证显示，不要求模型主动使用发布工具；显式发送过的同一答复不得重复。

恢复原有菜单分组、适用入口、层级与返回。菜单首页到参数、模型、保存、目录、历史及返回在同一张已确认卡片内完成。主动从平台菜单重新打开可以产生当前位置的新入口；卡片内导航不能默认另发。内容、选项、当前值、成功反馈和错误必须说明实际操作，去掉无助于判断的泛泛说明。保留有用的 Slash 命令，不恢复已取消的 Cron、原生人工接管和历史改写功能。

恢复旧执行展示：排队、开始、同轮过程卡、阶段性正文、计划、文件变化、适用工具活动、压缩状态、停止、失败、原生问题、最终 Markdown／代码／长文／图像与可验证的用量信息。保留 quiet／normal／verbose／chatty 的原有区分，只展示后端实际提供且可对用户公开的事件，不暴露原始敏感工具负载或模型私有推理。复用原渲染与归并能力；每个 token 不进入业务持久日志，最终正文和阶段事实必须可恢复、顺序明确、去重。

私聊的停止只作用于选定私人执行及其原有待派发用户输入，不因看过某个项目扩大到整个项目。停止后新消息可正常处理，无需另按继续；旧轮的自动继续不能借新消息的准入重启。项目暂停／恢复仅在明确的项目操作或实际自然语言指令中使用。菜单不无条件并排放暂停和继续。查看历史／项目不暗中发起工作；明确切换或进入关联讨论才改变后续输入归属。

### 群里呈现团队汇报

主群显示负责人对人的回复、需决定的问题、重要变化和正式交付。话题围绕人关心的工作组织，不按每个内部子任务生成一套执行屏幕。成员内部讨论和任务状态可快速更新，飞书展示按实质变化归并。

默认不广播思考、逐 token 输出、每次工具调用、内部交接、可自行恢复的重试、秒级计时或无变化的心跳。不伪造完成比例，也不将某个成员结束一轮当作任务完成。人可按需查看分工、协作记录和成果；负责人可按人的参与约定多汇报或少汇报，但不得因此绕过频控。

进展默认在稳定卡片内更新。普通状态和完整可读段落同卡最多每 30 秒一次，仅内容有变化才更新；整个群后台展示至少间隔 10 秒，跨 Bot 共用预算。首次重要状态、真人操作、需决定、明确阻塞及正式结果优先，不等待普通进度窗口，仍服从平台硬限额。最终结果到达时取消过期的待发进度，不在完成后回放工作中状态。固定导航与首页不随每次工具事件重写。

这些数值是产品默认值，不是平台额度。飞书[发送消息文档](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/reference/im-v1/message/create?lang=en-US)明确同群 5 QPS 由群内机器人共享。发送、回复、更新、上传分别使用适用限额；应用跨群还需共享应用预算。优先在进入发送队列前保留最新状态，调用层再节流、按平台冷却退避，不能把大量旧进度排队补发。未知发送和未知 PATCH 核对原操作，不盲目重发。

### 内部协作和对人发布分开

| 场景 | 默认能力 |
| --- | --- |
| 私聊助手 | 回复绑定的私人对话；按人的任务发送文件／图片，保留临时分享和正式成果的区分 |
| 群负责人 | 当前项目范围内的对人回复、汇总、问题与正式交付 |
| 普通专家 | 执行任务、内部消息、保存文件和版本、把结果交给负责人；默认不向群发布 |
| 真人直接点名或明确回复的专家 | 对这条真实输入或对应话题作有限回复；不是获得整个群的泛发权限 |
| 明确获交付委派的专家 | 在指定目的地发布获授权的内容类型及成果版本，不要求每次由人重复确认 |
| 后台评审 | 内部交接结果；真人发起的私人评审由系统返回原私聊 |

保存文件、发给同事、发给人是三个不同动作。专家保存草稿和版本不自动把它加入群通知。正文答复同样限制在获授权的会话／话题。普通答复可以包含必要链接；它不自动修改文档访问权、上传附件或登记正式成果。正式交付、资料索引和原件授权仍按清单与资料权限处理。

当前受管进程已不注入旧 `codex_remote_feishu` MCP，旧 Bearer 也被清理；风险来自新 CLI 的发布命令仍对普通专家开放。整改按可信 scope、角色和本轮来源投影工具发现／指令，同时在业务服务和真正发送前校验。隐藏工具或改提示词不能替代授权。

私聊可通过新受管服务提供与旧发文件／图片／视频相容的工具体验；不能恢复旧任意目的地凭据。普通群专家不获得泛用飞书发送 MCP。读取授权资料、评论、图像理解和用户自配研发 MCP 独立保留。直接提及、明确的交付要求和负责人委派必须有实际输入或持久委派依据；模型不能通过传入任意历史 message ID、换幂等键或自报角色获得发布权。角色、任务、Bot 或群变化使旧授权失效；未知结果仍只恢复原发送。

## 实施拆分与所有权

主代理负责产品边界、共享接口、群展示和频控、整合、文档及最终发布。三个便宜子代理各有独立代码范围；共享文件必须先协调，不以缩减用户已确认体验解决实现困难。

| 工作包 | 内容 | 主要代码范围 | 完成证据 |
| --- | --- | --- | --- |
| A 菜单与单聊控制 | 旧分组、单卡导航、设置／目录／历史返回、实际说明、私聊停止与新输入、平台菜单兼容 | `app_work_private*`、preferences／pickers、`workui` 导航、`private_stop`、`feishuapp/team_menu` | SDK 真实回调一路点击，平台消息 ID 不变；查看项目后停止只作用私人执行；新输入可继续 |
| B 单聊执行展示 | 精确原生事件关联、旧过程和最终渲染、详细程度、同轮顺序、去重、暂停／失败／问题反馈；受管私聊媒体能力 | runtime／wrapper 事件、专用私聊输出模块、daemon 接线、相关渲染器 | Codex／Claude 真实协议子进程不调用 publish 仍有正常最终答复；过程同卡、群不泄漏；重放不重复 |
| C 发布权限 | 负责人／专家能力差异、真实直接回复、明确委派、文件版本限制、CLI 发现、服务与出站验证 | `workservice` 发布／授权、grant 存储和领域、CLI 发现、受管媒体授权 | 普通专家直调服务被拒但内部交接正常；真实点名／委派有界成功；伪造来源和撤权失败 |
| D 群展示与调用调度 | 30 秒卡片合并、10 秒群后台预算、跨 Bot 额度、优先级、终态淘汰、避免长期卡错误重放 | project views、publication 调度、store 展示记录、Feishu broker | 多成员并行及故障下实测请求次数／目标／顺序；需人事件优先，过时状态不补发 |
| E 整合复核 | 对照旧体验、完整使用旅程、双状态机、文档单一事实源、发布 | 上述跨组件边界 | 全仓、race、Windows 构建和提交检查；真实平台验证单列，不冒称已验 |

发送地址必须显式区分普通私聊、群主会话和群任务话题；私人新输出调用 create(chat_id)，不能通过 reply + ReplyInThread=false 模拟直发。原始消息关联保留作授权证据，实际发送投影单独冻结。单卡展示归属应覆盖导航流，同时保留业务目标、身份和版本校验，不能简单把所有业务卡改成同一个 key。私聊输出与群汇报不能都由一份群提示词控制。

## 从用户实际操作验收

1. 从平台菜单打开，进入参数→模型→保存→返回→工作目录→选择→历史→返回，检查实际 create／PATCH 请求及同一消息 ID；对转发卡、旧卡、失败更新也检查下一步是否明确。
2. 连续发送普通私聊，普通答复、图片和操作卡留在主会话；显式引用仍指向正确工作。四种详细程度按真实事件展示，最终正文无需 Agent 调用 CLI。长输出、计划、工具、提问、失败、重启和重复事件顺序正确。
3. 私聊查看项目后停止当前私人执行，项目其他成员继续；取消的私人待发消息有记录；新消息能够启动新执行，旧轮不会自行恢复。
4. 群内负责人安排至少两名专家，产生密集内部消息和结果。后台协作照常推进，群无思考流／逐工具更新；多任务状态只产生受控汇总请求，正文按完整内容更新。
5. 专家保存文件并内部交接，群内没有附件或成果通知；负责人选定版本后正常交付。真人点名专家可以收到限定回复，明确文件交付和负责人委派可用；伪造来源、跨任务／群、被撤销授权、改幂等键重复发布均不能绕过。
6. 普通状态排队时插入真人操作／决定／完成，验证优先级和最终状态不会被迟到进度覆盖。限流、网络结果未知、进程恢复及卡片更新失效时不刷屏、不丢正式结果、不影响内部队列。
7. 单个 Bot 服务多个群、多个 Bot 服务同一群，实测共享额度。只检查每个 Bot 自己的测试不算通过。

## 验证边界与实施记录

本方案先落文档再实施。隔离 SQLite、实际 CLI 可执行文件、SDK HTTP／WebSocket 与受控原生子进程用于自动使用旅程验证。真实飞书桌面／移动客户端、真实模型和租户权限另记实际证据；没有实际运行不得写成验收通过。不得为了验证向未指定的真实用户或群发送消息，或擅自部署／重启现有服务。

## 模型目录再次实测后的修正（2026-11-23）

用户在 `b57b4f22` 上实测模型页仍为空，刷新无效。实际两张菜单记录明确返回 `carrier_disconnected_reconcile`；当前 worker 代次 3 已离线、无原生会话、无执行占用。已有十项模型的两份原生目录都来自部署前。先前测到的约二十毫秒只说明旧请求的 RPC 耗时，不能证明新版端到端可用。

根因是三个仍然存在的错误边界：五分钟 TTL 隐藏旧目录；OAuth 执行 AuthGeneration 随重启变化，被误用为目录身份；刷新仍要求当前业务 worker 可恢复。异步查询失败又未完整投影到等待卡。旧版长期保留成功列表、失败不清空的行为没有真正恢复。

本轮将目录读取独立为配置服务：临时 Codex 进程只做初始化／账号核对／模型读取，最多两个并发，不经过业务 Host。持久 profile 目录按稳定账号、提供商及配置范围保存，旧成功结果长期保留，更新失败只记录失败原因。队列满时显式刷新保存意图，账号切换、分页和迟到结果分别校验。旧 worker 目录缓存不再作为菜单的第二个事实源，执行代次与业务恢复规则不放宽。

在当前机器实际调用新的独立查询路径，先核验 ChatGPT 账号，再查询得到十项模型；模型探测完整临时进程约 991 毫秒。此结果只证明当前机器该次真实查询，不等于所有客户端或网络环境的时延保证。整合验收还要求覆盖原先的离线恢复会话、重启后长缓存、刷新失败保留选项、原卡自动更新，以及查询满额后的显式刷新。

本轮整合验证通过全仓 `go test -p 2 ./...`、daemon／workstore／worksettings／codexprofile／codexoauthstate 全包 race 和 Windows 主程序构建。实际 SDK 覆盖冷加载后原消息 PATCH、失败保留选项、同脱敏提示但实际不同账号的迟到结果拒绝、导航和身份变化，以及分页公平推进。永久缓存跨存储重启、满额显式刷新持久排队和原生凭据在查询中变化不污染旧缓存均有回归。

## 单聊真实使用故障与架构边界纠正（2026-11-23）

线上顺序为：原私人会话停在离线恢复；真人消息的原件仍排队，系统另建管理副本；管理会话没有继承用户的 full access，尝试运行内部状态命令时要求批准；用户改的是原会话设置；随后取消决定因 native operation 的 target 错设为 request ID 被发送登记拒绝，却被记录为 unknown，界面将点击标成 handled。没有原生答复命令的登记记录，所以这不是用户没有等待够久。

本次纠正的架构边界：一个私人会话直接使用用户选定的原生后端与会话历史。共用持久输入、记忆和恢复代码不代表共用团队产品流程。普通单聊不再自动转入管理 Agent，不要求团队分派与工作汇报仪式；Slash、设置、停止与确认由宿主确定性处理。群负责人及成员协作保持原产品边界。

- 删除个人消息的自动管理副本入口；历史 pending 副本取消且保留原件，运行中的历史副本按实际执行证据结算。
- 恢复旧个人权限默认与设置显示，避免模型/Profile 选择顺带清除旧权限。
- 纠正原生答复的 worker 归属，区分根本未发送与发送结果未知；历史取消决定按原持久来源恢复，不擅自批准。
- 补齐未开始执行的离线进程恢复和已静止进程恢复，保留原输入与会话归属。
- 私人提示词独立于团队提示词。收到消息、后端就绪和上一轮结算直接唤醒处理，避免逐段等待轮询。
- 恢复图片暂存、图文合并与顺序，反应展示及人的反应操作，公开过程摘要与原生 usage 显示。
- 可变执行设置与连接身份分开：调整权限、模型和记忆不再默认丢弃私人原生历史；变更账户、提供方或工作目录仍按实际身份重新准备。
- 点赞追加包含精确的暂存图片组；鼓掌保留旧版文本和附件引用注入及仅反应的成功反馈，内部使用独立会话操作和真实结果，不挪作模型轮次的输入接收证明。停止后的新图不会借用停止前的说明文字执行。
- Claude 已关闭输入的旧轮次仍可接收迟到最终结果，但不能再把新输入确认成旧轮次追加；原生确认在最终发送登记前复核终态，避免发送过期决定。

验收按真实 SDK 事件与实际 wrapper 协议子进程进行：普通消息连续两轮、排队与执行中追加、图片后文字、重复与撤回、下载失败与超额恢复、明确取消后下一条输入、退出和重启后原会话续接。测试中的原生响应受控；是否已在真实飞书客户端呈现，须与服务端接受发送区分，不能用单元测试结论替代真人观感。

现场副本验证：使用线上 SQLite 的只读备份，在隔离副本证明原私人 worker 可恢复为同上下文待准备状态，两条原始真人输入保持 pending；取消确认的旧 operation 同样在禁用 transport 的副本中完成精确目标修复。两项验证均未修改线上数据库或重发用户消息。

独立 shell 输入的数据库约束迁移也在实际线上库副本验证：原 105 张表行数不变，全部 inbox 的 ID、revision 和 payload 摘要不变，外键检查零错误。永久回归另含入向级联外键保留，以及迁移后发现外键错误时整笔回滚旧约束和原数据。

### 按旧单聊重新核对（2026-11-23）

以改版前的 `36b1e1e6` 对照三种入口。飞书底部应用菜单和手输 Slash 使用相同的命令目录、别名和参数处理。点已有菜单卡时保留该卡的身份、返回路径和版本检查。项目列表、资料和设置总览仍可从已经发布的专用菜单键进入。

普通私聊在本次输入里保留真人原文和所附图片。宿主另附已接收的输入 ID、持久消息 ID、飞书消息 ID，以及本轮调用工具所需的执行引用。长消息保有完整正文的读取入口。排队、点赞追加和鼓掌操作继续以原始消息及原生接受回执判定归属。团队任务使用原有结构化输入。

显示详细程度在原生事件投影时读取，调整档位后可继续用当前进程和会话。实际改变执行权限、认证或模型时，准备和派发用相同的启动兼容判断。Codex 跨已知模型组时沿用旧会话切换规则，参考当前连接和会话已经观察到的模型；没有证据不会推测当前提供方选了哪个模型。进度跨卡时带上仍在进行的活动，普通文字回复只产生答复卡。

普通私聊的最终正文或原生 diff 需要预览时，宿主先持久保存已确认的终态，再通过本人消息和这次本机启动记录核对 Bot、接收者和目录。在独立队列调用原有的 Drive／网页预览服务，按处理后的完整正文拆卡。多文件中部分生成成功时保留已经生成的链接。服务不可用则显示原文；上传已经开始、重启后无法确认结果时保留原文，避免再次上传。预览等待不触发人工核对提示。后台收尾后继续原来的输入结算。群成员的内部答复仍走原项目发布规则。

验收覆盖旧编排器与当前私聊对同一组原生事件的可见输出对照、飞书 SDK 菜单连续点击、Codex 与 Claude 的受控协议子进程、图片与两种 reaction、重启后恢复，以及预览多卡、失败和不确定上传。使用线上 SQLite 只读备份核对了全部四条既有展示记录，三条普通私聊可以解析本人及启动目录，旧管理会话没有预览资格。该检查没有向飞书发布历史文件。飞书客户端的排版和实际账号访问链接仍需区分于隔离 SDK／协议测试。
