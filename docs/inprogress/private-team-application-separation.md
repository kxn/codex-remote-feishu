# 单聊与团队应用分离：设计、实施与验收

> Type: `inprogress`
> Updated: `2026-11-25`
> Summary: 记录独立单聊与团队应用的设计、连续操作的实际接线、停机恢复证明与验收边界。

## 1. 已确认的决定与当前事实

用户已批准两套应用独立：单聊保持改造前直接使用 Codex／Claude Code 的体验；群聊围绕长期成员、任务和持续协作组织工作。共用平台通信及原生后端能力，不能共用团队业务状态机来实现单聊。这一决定替代旧团队设计中“单聊最终统一进入团队执行内核”的要求。

基线核查还确认旧版支持 OpenCode／ACP。它没有被用户取消，也属于单聊恢复范围；原生协议的能力差异需在适配层解决，不能通过删菜单或永久禁用后端绕过。

本文是本次改造的设计与实施依据，标记为计划的内容不是已上线事实。当前代码基线为 `e9463037`；旧单聊行为对照固定为 `edffb35f`（2026-11-20），团队实现前的文档提交 `36b1e1e6` 也可用于对照，但不是另一个行为标准。Raft 参考固定为 `db5e399f017d584e49597e3a28757645d6807893`。旧版同样需要验证，不把历史提交当作无缺陷证明。

### 1.1 保留代码库，替换错误的业务耦合

不全仓回滚，不再重写 Codex／Claude wrapper。保留现有团队持久任务、资料、发布权限、原生证据、恢复和飞书发送能力。单聊不以最近几轮修复代码为行为标准；优先复用旧版完整业务路径和经过核验的后续通用修复。近期补写的团队私聊适配只在迁移期用于读取、停止、结算旧会话，完成切换后退出活跃入口。

旧单聊核心仍在 `internal/core/orchestrator`，已由独立私人应用接入中立 Feishu gateway；历史失效不等于全部代码被删除。与此同时，`workhost`、`workruntime` 依赖团队存储、Attempt 和报告，不可原样称作公共运行层。

### 1.2 明确不恢复的功能

用户已取消的 Cron、VS Code 人工接管和 `/bendtomywill` 不恢复。旧群工作模式不恢复。群团队不要求用户管理 worktree；私聊保留原有工作区入口，选择现有目录、模型、账户等精确设置仍保留明确界面。私聊保留原设置已启用的自动临时预览和 diff 链接。群聊维持低频展示与有边界的正式发布。

## 2. 人实际使用的两条主线

### 2.1 单聊

用户选择后端及工作目录后，消息直接进入当前原生会话。菜单、Slash Command、模型目录和本地设置不依赖团队任务或成员调度。执行中使用原有反应、队列、图片暂存、点赞追加、鼓掌追加、停止和原卡更新；最终答复自动回到普通私聊。

没有选择工作目录时，延续旧版目录选择流程，不悄悄在私有临时目录开始代码工作。私聊记忆由私人应用按真实用户与 Bot 身份管理，恢复会话时提供受限索引；得到记忆能力不意味着进入团队任务流程。

用户另行确认需要显式的项目查询和分享入口。查看项目资料须明确选择有访问资格的项目；分享须明确接收项目和具体正文或资料，并提供真实交付回执。私聊始终保持私人身份，不共享整个私人 transcript，不改变当前私人会话归属或 cwd，也不因查看项目而获得群任务控制权。旧产品稿中靠提到项目名自动切换工作身份的描述不再适用。

### 2.2 群团队

用户主要与负责人沟通。长期成员持有职责、项目经验、收件箱和稳定资料入口；任务记录工作承诺；实际执行会话可以恢复、重建、并行或结束。这三者不得通过同一个 ID 或生命周期替代。

成员在同一项目中的连续性不随任务完成或原生会话重建消失。默认讨论面向成员，只有需要承诺、分派、依赖或交付时才形成任务。已有明确任务关联的消息仍应到达对应执行，不能一律送到一个巨大的公共上下文。

负责人先处理沟通和组织工作，长操作可委派给具名成员或受支持的原生执行助手。两种委派不同：具名成员有独立项目身份和收件箱，执行助手只对父执行负责，不获得群发布身份。负责人可达性需要实际投递及调度验证，提示词不是完成证据。

### 2.3 工作中变更

用户中途修改要求，负责人能接收并传播给受影响成员。后台记录消息已保存、已送入原生执行、被成员处理三个不同事实。支持忙时输入的后端使用有明确回执的追加；不支持时保存为待处理输入，必要的停止走显式控制通道，禁止假称已送达。

需求版本变化与输入投递分别处理：收到补充消息不等于原有副作用已撤销，也不自动把一次回复视为任务完成。

负责人正式修改任务要求或接手成员时，任务要求代次与责任代次是停止旧执行的持久依据。控制器向旧载体的准确会话、turn 发送停止，并等待原生执行、自动续轮及后台进程的实际停止证据；发送成功不会提前释放任务占用。旧执行尚未提交处理报告也可以作为“被变更中断”归档，不制造任务成功或要求人批准旧要求。

未处理的输入仍保留。仅修改要求时，它们与变更通知一起进入当前版本；换接手成员时，建立新的收件记录，沿用原消息、附件和来源，原收件记录标为已转交所终止。仍被旧执行领取的输入必须等旧执行结算后才能转交。旧版结果留作历史材料，不能覆盖新任务检查点或继续发布业务结果。任务占用直到停止核验后才释放，避免新旧负责人同时执行同一任务。

## 3. 应用与公共能力的边界

```text
飞书认证事件 → 唯一入口路由 → 单聊应用 → 原生执行接入 → Codex / Claude / OpenCode
                         → 团队应用 → 原生执行接入 → Codex / Claude / OpenCode
两套应用 → 公共飞书发送层（限流、重试、已确认消息更新）
```

| 所有者 | 唯一负责的事实 | 不负责的决定 |
| --- | --- | --- |
| 平台接入 | 身份核验、事件键、原始入站、附件来源 | 菜单归属、任务分派、队列消费 |
| 单聊应用 | 私人会话选择、输入队列、图片组、菜单、显示及私人记忆 | 团队任务、成员授权、群发布 |
| 团队应用 | 成员、项目、任务、内部消息、项目资料、发布授权 | 私聊菜单和私聊原生会话选择 |
| 原生执行接入 | 进程和会话身份、输入接收证据、运行事实、命令关联 | 工作是否交付、是否通知人、哪个项目完成 |
| 飞书发送层 | 发送尝试、平台 message ID、重试与限流 | 把内部结果自动变为群消息 |
| 公共配置 | Bot 身份、账户、用户明确设置的公共默认值 | 隐式覆盖某项目或私人选择 |

使用同一仓库和服务。应用不得直接读写另一应用的内部状态；跨应用功能使用查询、分享和授权端口。公共包不能依赖任一应用的业务类型。数据库是否同进程不是隔离证明，写权限和存储接口必须独立。

这里的分离是业务归属、执行和交互状态的分离，不是进程故障隔离。当前 daemon 统一初始化平台身份存储及团队运行设施；团队数据库或基础设施初始化失败仍会阻止整个服务启动。没有创建项目、没有团队任务不影响普通私聊。私聊查询 Bot 身份和显式项目授权经过平台适配端口，不以团队任务或处理报告驱动私人会话；本文不承诺两套应用可独立部署或一侧启动故障时另一侧继续服务。

### 3.1 唯一执行归属

每个原生载体注册时冻结应用类型、应用内部 owner、代次、后端和实际进程身份。业务 owner 对公共层是不透明标识。命令和事件必须精确匹配该注册，不根据当前聊天选择、ID 前缀、先到先得或“处理失败就交给另一边”判断。

同一个载体不能同时注册给两套应用。原生会话 ID 必须带后端及账户/运行命名空间，不能单独全局比较。私聊不得为满足公共接口而创建虚假的团队 Task、Attempt、ProcessingReport。

团队旧 worker 协议 v1 的 role/scope/context/worker/attempt 字段仍保留在团队侧；私人载体以独立应用 owner、代次、连接和进程身份注册。旧载体恢复须验证实际 binding 和原生证据，不能只改字段名而借用团队表中的执行权。

### 3.2 唯一入站归属

普通消息按可信 chat type 和 Bot 绑定确定应用。卡片按发出时保存的应用归属、平台消息 ID、版本和生命周期定位。无 chat type 的反应/撤回根据原消息归属定位；Bot 菜单属于私人应用。不能通过模型判断入口，也不能根据当前项目导航重新解释旧卡片。

入站必须先持久保存，再确认 SDK 接收。去重和队列消费的原子性不得因拆应用丢失。菜单操作不被模型执行阻塞。未知旧卡给明确失效提示，不触发另一应用的 fallback。

### 3.3 展示与权限

单聊自己把原生输出、问题、进度和最终答复投影成旧体验。团队只发布经授权的消息和资料，原生结束不是群通知。共享发送调度器保留账号/接口限流及交互优先级，群状态合并不能挤占单聊交互。

运行时工具按应用和本次身份签发。私人发文件工具不能成为团队成员的旁路；执行助手不继承父成员的公开发布身份。提示词、CLI 帮助和服务端授权从同一能力定义派生。

## 4. 目录、记忆与资料

### 4.1 稳定归属

成员长期工作空间按项目与成员稳定定位；私人记忆按用户与 Bot 身份稳定定位。它们不以任务或原生 session ID 命名。项目共享资料维持项目级入口。源码及随代码演进的文档留在用户选定仓库，Agent 准备与管理 worktree。

cwd 是某次执行的参数，不能决定记忆属于谁。临时执行目录只放可丢弃中间物，不能默认承载唯一一份长期成果。

### 4.2 恢复与发现

每个稳定工作空间具有小型恢复索引，包含当前工作、关键决定和资料指针；详细内容按需读取。索引和业务资料分别确定权威原件，生成出来的索引不是另一份可独立编辑的同名事实。现有 scope memory 的来源、授权和版本能力保留。

单聊的恢复索引通过仅向该私人载体提供的 `private_memory` 工具发现。索引只返回适用范围、来源和版本；正文按准确版本读取。保存、修订、撤销和幂等回执写入私人 journal 的同一事务，旧版本保留但不作为当前答案返回。换模型、原生 session 或 cwd 不改变这份记忆的归属。保存内容限于长期偏好和已确认决定，不把全部聊天、短暂执行进度、凭据或无关项目资料塞入记忆。

受管理的私人载体和团队载体均关闭 Codex／Claude 的自动长期记忆写入，避免用户与项目之间经同一个登录目录混入另一份未授权记忆。原生上下文压缩、用户指令文件、工作目录和登录目录保留；这些不是系统长期记忆的替代存储。未进入新应用的独立旧 wrapper 不改变其原有设置。

旧数据导入只允许原 personal scope 的私人记忆，不复制 team/role 共享条目。切换后这份私人记忆由目标应用管理；修订或撤销会遮蔽不可变导入记录，不能重新退回旧版本。未来若开放跨域共享，必须另行定义共享来源的实时授权，不能把当前私人导入当作共享授权。

成员重建原生会话时能读到自身项目索引；其他项目和私人内容不能因同 Bot 或同机器被自动注入。目录不是 OS 沙箱，不能据此宣称 full access 进程无法读取其他目录。

从旧 context 目录迁移时不批量猜测文件归属。保留旧文件并登记来源、所属工作和可访问入口；明确属于某项目/成员的资料再进入稳定索引。切换 cwd 不自动搬文件。提供受授权的发现能力，避免只有“已正式交付”的文件可找。

## 6. 迁移与恢复

迁移以私人 owner 为单位，有持久阶段：准备、停止接收旧流程新工作、排空/核对、导入、切换、完成。新到输入保存在确定的缓冲 owner，切换前后不会双消费。

1. 保存旧私人导航、队列、图片引用、原生会话、cwd、账户、权限、记忆及待发送输出的来源快照。
2. 旧流程只处理已有执行的停止、回执、输出结算，不能启动新的私人执行。
3. 精确核对活跃载体、输入是否已被原生接收、后台及续跑是否停止。未知投递不重发，保留具体可恢复状态和逃生入口。
4. 导入到私人应用；原生历史可恢复时保留原 session，不以导入失败静默 `/new`。队列、图片、设置和临时预览规则一并导入。
5. 原子切换 owner epoch。重启重复执行迁移不会重复投递、重复发最终答复或覆盖新设置。
6. 旧卡只恢复被明确支持的原操作；无法安全映射的卡提示已失效，并提供当前菜单入口。
7. 团队项目和在途团队任务不被私人迁移停止。完成后删除新输入可达的旧私人路径。

回退不能简单运行旧二进制：已有新应用写入时必须通过逆向迁移或保留新写者，禁止两个 schema/应用同时控制 native session。实施期间不自动升级用户线上服务，待迁移与完整旅程证据满足后按发布流程部署。

### 6.1 必须导入的事实及冲突处理

| 现有来源 | 新所有者及处理 | 不能采用的捷径 |
| --- | --- | --- |
| principal、RoleBotBinding、原始 SDK 的 tenant/App/user/chat | 私人 owner 保留真实平台身份与 Bot 绑定代次；surface 只是交互关联 | 根据 gateway 名、最近聊天或模型名认人 |
| PrivateNavigation.FrontContextID、context preferences | 私人当前会话与会话设置；项目查看仅保留授权引用 | 将 project view 当成 cwd 或把私人记忆移入项目 |
| worker 的 namespace/session、冻结 launch 的 cwd/profile | 有停机证据后导入原生恢复目标；新的 carrier 注册到私人 owner | 只复制裸 session ID 或复用已失效的 worker token |
| 待处理 Inbox、原始 message、附件 content、撤回与 reaction | 转为私人入站与待处理输入，保留原顺序和图片簇、已接收证据 | 重放所有历史消息，或只搬最新一条文字 |
| sending/unknown admission、未结束 native turn | 旧 owner 继续核对；新 owner 不领取，保留完整恢复依据 | 把 daemon 重启当作原生已停止，或把有最终文本当作输入都已处理 |
| 旧 publication/outbox、private preview operation | 已确认平台消息继续关联；未知发送由原发送记录核对 | 新 owner 再发一张最终卡“保险” |
| scope memory 与其 sources/revision | 显式导入私人记忆或授权查询；保留来源与修订关系 | 将个人偏好提升成 Bot 全局或团队共享事实 |
| 旧 context 目录 | 记录位置与所属旧工作，供有权限的恢复查询 | 自动移动全部文件、删除目录或把当前路径存在当历史身份已证实 |

### 6.2 公共端口与应用日志

`executionowner.Registry` 管理载体与会话的独占归属。`Register` 发生在 launch 前，native session 尚不存在时也能登记；`BindSession` 仅接受原生事件确认后的会话身份。停止后新 incarnation 可恢复原会话，不能把 session ID 的历史归属做成永久占用。`Resolve` 必须带已认证连接冻结的 epoch，迟到事件不能被重新解释成新 owner 的事件。`Retire/Transfer` 的证据由可信 verifier 验证，重复同一结果幂等、冲突结果拒绝。

`privatechat` 复用旧 orchestrator 作为私人业务内核，独立 journal 管理 SDK 入站和派发事实。入站全局去重使用可信 tenant/App/event 身份，不随 `/new`、会话切换或迁移 epoch 改变。输入、控制和只读核对分别调度；未知停止不能阻断读取状态及核对入口。准备派发、发送前记账、原生接受或结果未知分别持久保存。只有通过 `NativeLease` 核验的已提交原生事件及实际请求关联可以证明 accepted；不存在由调用者传入 JSON 就结算输入的兼容入口。

恢复读取必须可以枚举完整 prepared/sending/unknown 记录及原输入、命令、绑定和证据，不能要求重启后的调用者仍记得内存中的 dispatch ID。SQLite 数据库预先以 0600 建立，启用可靠同步，检查 schema 版本并持有进程独占锁；未取得单写者身份不能改写 sending 状态。

旧 core 的队列作为已持久输入的交互投影；投影不能成为第二份“消息是否已交给模型”的事实来源。已有私人 `Service()` 装配口仅供宿主复用旧回写能力，暴露指针不等于隔离完成。发布前必须证明所有活跃入站、回调、原生事件和回写都经过唯一应用归属检查。

### 6.3 原生接入必须补齐的协议差异

连接认证与应用类型分别记录：私人载体和新团队载体都必须走已认证的精确连接通道，但团队载体不能因此被当成私人会话。握手、命令发送、事件提交和事件回执须形成同一条真实 WebSocket 链路；只验证内部调用不足以证明接线。旧连接提交的事件回执不能按 instance 查询后来连接再发送；重连重放则由新连接重新核验已提交的事件。历史团队载体只按已持久保存的旧启动协议兼容，不以认证失败作为回退依据。

代码追踪确认：旧私人 headless 启动不传团队 launch snapshot，wrapper 因而不启用团队 journal。旧 `CommandAck` 仅证明 wrapper/传输处理，不能证明 Codex 或 Claude 已接受追加输入。直接复活旧入口或把私人输入改造成团队 Attempt，都不能完成本次分离。

在现有 wrapper 内增加明确的私人原生模式：冻结应用 owner、代次、载体 incarnation、真实后端和历史命名空间；执行 ID 是私人会话自己的本轮标识。私人 launch 不包含角色、任务、报告或团队工具凭据，不改变用户原有 model、approval、账户、cwd、system prompt 设置。团队 v1 launch 和 journal 保持兼容；同一启动不能同时声明私人和团队 binding，同一 journal 不能重新绑定另一 owner。

私人启动和忙时追加分别验证：启动依据原生请求与 session/turn 的精确关联；追加依据后端对应请求的 accepted/rejected 事实。没有这些事实就是未知，不能拿 transport ACK 或“出现了输出”代替。两个后端复用原来的译码器和原生通信，不重新造一套 Codex／Claude wrapper。

出站边界涵盖命令本地准备到 socket 写入结束。迁移先持久禁止新业务发送，保留精确停止和检查命令；取得持久原生/后台检查结果后，关闭该载体全部发送并等在途调用结束，再核验真实 OS 退出及检查水位之后没有副作用写入，最后切换执行归属。等待超时不能重新开放发送。该发送边界与 daemon 单进程锁配合；重启必须先恢复持久禁止状态再开放入口。它不阻止原生证据继续入库，也不把“socket 已排空”当作模型已停机。

### 6.4 私人恢复不得改变旧交互

旧内核的必要状态采用明确字段清单保存：会话/目录/个人覆盖设置、队列和媒体来源、冻结的 dispatch 关联、单调 ID 水位。历史状态不得伪装为新进程已在线。快照、已应用输入游标和待执行效果同事务提交，提交之前不执行发消息、启动进程或发原生命令。

原来点赞/鼓掌与图片组如何选择输入，仍由旧内核确定；持久层只校验该冻结计划的真实来源、归属和是否已消费，不另外发明队列选择规则。Bot 公共默认设置继续由公共配置恢复，不能塞入某一个私人 owner 的快照后反向覆盖所有人。

应用消费以每一条入站的 applied 记录为准，与快照及效果同事务提交；单一最大游标不能证明所有之前的输入都已处理。这样菜单可以越过等待核对的文本，文本仍然留在待处理队列。命令 ID 及旧核心实际选择的队列项、图片来源、自动续跑来源在提交前冻结；随后发送不得改选队首。效果使用可重建的版本化格式，派生的 renderer Payload 不另存为第二份事实。

恢复时只有存在未核对执行/投递的部分才受限制。菜单、状态和本地导航保持可用；没有在途执行的正常重启不得强制出现“需要核对”卡。带副作用的继续、停止和会话变更必须通过当前原生身份及证据处理。未知后台发送不能阻断交互卡片的独立通道。旧 callback 是否仍可使用，由发出时的归属、版本和生命周期确定，不由当前选中的会话重新解释。

### 6.5 单聊发布、原卡回调和执行展示

发送结果未知的私人卡片，在实际点击请求内有界读回同 Bot 原始卡片及冻结 token，核实后同步执行并返回原卡更新；失败只提示重试，不在后台消费导航后丢弃其同步返回值。

同步原卡更新会生成新按钮 token，并与输入、checkpoint 及 raw response 一起持久保存。中立路由只登记“已提供的同步视图”，不伪造平台发送回执；后续操作核对原消息归属和最新视图，连续多级导航与返回都经过相同入口。

原卡同步回调是 SDK 请求的返回值，不是另一条飞书消息。其最终 raw card、目标 message ID 和已处理入站在同一事务保存；平台重试返回原响应，不重新跑菜单，也不占用异步发送队列。目录浏览等短只读观察可以在规划阶段执行，但观察结果必须冻结；创建目录、下载/搬移文件、启动与发送要在提交后执行。

异步发布先冻结真实 renderer 的完整卡片结构，再逐条保存调用状态及平台返回的 message ID。批量中前一条已成功、后一条未知时，不能整批重发。SDK UUID 只帮助平台有限期去重，不是永久去重证据。最终预览与 diff 按旧设置生成；发送回执经唯一私人 Processor 写回旧核心并持久保存，不能由后台直接改另一份 Service。

预览第一次生成超时后，旧版的二次生成行为保留：实际最终卡回执确定后，持久安排重试并只更新那张卡。更新目标单独使用 `MessageDelivery.TargetMessageID`，不改写原输入的 `SourceMessageID`。已确认的发布前缀可在重启后跳过，确定尚未调用的平台操作可以继续；真实发送结果未知的操作仍等待核对。

进度快照与飞书消息的发布速度可以不同。业务和原生事件继续处理，平台发送结果未知只暂停同一显示链。每个原生载体、会话和 turn 的进度链，在首次渲染下一张卡之前读取已确认前驱的真实 message ID/窗口，使用旧进度分页算法确定更新或换页，并保存最终 payload。独立菜单、停止命令和新会话不等待另一条进度卡。不能通过堵住原生完成事件来保证卡片顺序。

### 6.6 平台入口的接线顺序

首先抽出只包含平台事实的消息、卡片、菜单和 observation 类型，Feishu gateway 不再要求私人应用依赖团队领域。旧团队类型保留别名，存量 JSON 和字段语义不改变。

共同入口持久冻结 SDK 事件归属，随后调用对应应用的幂等接收端口。稳定去重键来自 tenant、App 和平台 event ID；Bot 配置代次是首次来源事实，不能因重绑配置而把同一事件变成新消息。应用提交后、入口确认前崩溃，重放的是同一归属与事件，应用依原键去重。同步回调的结果也保存，以便重放同一响应。

接收时间属于首次本地观察：保存在冻结 Source 中，但不参与平台事实去重。恢复原始 DTO 时同时恢复原 gateway 与接收时间，不能让消息重放时间改变队列顺序或成员资格观察时间。

卡片、reaction 和 recall 查原消息已确认归属；没有 chat ID 时仍须得到唯一可信映射。未知归属持久保留待解析，不能试探另一应用。Bot 菜单依明确私人聊天绑定定位；群成员变更只进入团队观察路径。平台 message ID 和卡片版本由发送/接收的可信回执登记，不能由卡片参数自证。

已有团队 `team_view` 指向不可变卡片正文，同卡换内容生成新 UIView ID；UIView 的数值 Revision 还会因发送确认和失效变化，不能拿它当呈现版本。负责人选择卡单独使用 `team_setup_ingress`，以其不可变 selection notice 及实际平台回执定位。新私人卡使用 `private_view`，由私人发布适配器持久签发并写入按钮；旧 `daemon_lifecycle_id` 不是逐卡版本。发送未知时持久等待真实消息核对，不因回调到达就授予执行资格。token 写入、同步替卡和回调响应均经过宿主与持久入口；未知平台结果的可信核对仍须完成，不能只凭入口包测试上线。

### 6.7 停机与共享资源的生命周期

停机先拒绝新的平台输入并等待已进入的 SDK 回调，飞书出站连接继续可用。随后停止两套应用的后台准入并收尾原生载体，relay 保留到停止回执处理结束，再发送原单聊停机提示并关闭飞书连接。最后拒绝新的 HTTP/relay 调用、等待已进入的处理完成，才关闭存储。

私人 worker 的调度停止与在途操作上下文分开：停止后不领取新的输入、逐 owner tick 或效果；已开始的发布、收据投影和 checkpoint 提交继续结算，再释放 worker 计数。不能用取消后台循环的信号中止已经改变内存状态的持久事务。

等待超时不是处理完成的证据。仍有回调、迁移或 worker 使用存储时，私人和共享团队存储都保持打开并报告未收尾；不能只因团队 scheduler 退出就关闭共享配置和迁移来源库。这个生命周期计数只保护资源使用期，不替代各应用的 owner、权限和原生归属检查。

共享执行注册表也等待团队 worker 退出。服务函数返回时，若任一应用、SDK 或原生回调尚未排空，不删除 daemon 的 PID/token 锁文件；下一进程必须等操作系统确认旧进程已经退出，才可清除失效锁。这与迁移依赖的“旧来源已停止”证明是同一条约束，不能通过一次停机超时绕过。

### 6.8 共享 Codex 维护与私人会话接续

单聊仍从 `/upgrade codex` 打开原有升级卡片，打开不会查询远程新版本。检查、再次检查、确认、进度与完成沿用同一卡片；过期或重复操作保存明确的拒绝结果，不形成永远待处理的控制命令。检查得到的安装来源和目标版本冻结在私人流程中，确认后由共享维护服务重新核验。检查失败不保留旧的可执行候选版本。

私人入口和团队入口只能登记同一套主机维护事务，不能各自启动安装器。 真人的确认输入及执行意图持久提交后即可执行；进度卡片发送失败或未知只影响那条展示链，不能成为额外的业务执行门禁。私人登记依据实际已确认的 owner 卡片和持久执行效果；跨数据库中断后以同一 effect ID 查找原登记结果，不重复创建升级。界面只展示共享维护的实际状态，重复查询和相同的核查错误不产生重复卡片；未知结果不能写成完成。

执行维护先禁止新的 Codex 业务发送，再保存各私人会话原先的调度模式并暂停后续派发。正在进行的原生执行仍须通过实际停止、检查和进程退出证据结束。恢复进程使用独立的“维护替换载体”路径，不复用切换工作目录的清理路径；后者会丢弃草稿，不能拿来恢复原会话。旧会话、cwd、账户命名空间、图片、排队输入、权限和模型覆盖值均保留。新载体必须通过真实连接、进程身份与会话归属核验，维护解除后才恢复原有派发模式；原本暂停的会话继续暂停。

团队中尚未真正启动的 prepared 载体与已启动载体分别核验。前者须有已阻止原启动的工作日志及 registry 从未登记的事实，不生成虚构的停机回执。它若带历史 session，还必须有该 session 原归属、原进程停止及明确转移证据；仅知道 session ID 不足以接续。Claude 和其他后端不受 Codex 的维护禁止状态影响。

### 6.9 连续操作的实际可用性

目录和会话选择不能把上一次的准备态当作本次成功。只有本次操作确实准备了可用载体，才显示下一条消息可执行；失联时保留已确认的目录与原会话，并由同一恢复流程接续。退出意图提交后，旧载体立即退出可接管候选，迟到的退出回执只影响旧载体，不得清掉新选择。

中断停机的恢复区分物理进程退出和任务结果。已有原生检查能够使用时继续沿原证明；wrapper 已退出而检查未完成时，以宿主进程身份、完整进程范围和排他 journal 证明物理退休。旧任务结果仍可能未知，不能伪造完成或自动重放；退出后新建保持可用。宿主库 v2 防止旧 reader 重写并丢失新证明，私人 journal 保持 schema 9。

平台底部菜单使用已经核实的私人聊天绑定补足目的地，保留原始 SDK 事实；不从历史消息推导新卡位置。临时文字增量拒绝不阻断同批后续持久事件，每条仍独立鉴权；持久事件失败则停止该批，保持结果次序。具体状态合同以[远程状态机](../general/remote-surface-state-machine.md)和[卡片状态机](../general/feishu-card-ui-state-machine.md)为准，逐用户流程的当前结果统一记录在[验收清单](./private-chat-baseline-acceptance.md)。

## 8. 用户旅程验收

| 场景 | 必须观察到的行为 |
| --- | --- |
| 新私聊→选目录→发 hi | 实际 cwd 正确；原生会话直接执行；主会话答复；不生成团队任务 |
| `/menu`、平台菜单、卡片返回 | 同一旧菜单规则；同卡更新；标题/Slash、当前配置、模型缓存及系统设置完整 |
| 工作中打开菜单 | 不启动模型，不等团队 scheduler，不出现核对执行卡 |
| 文本→多图→说明→点赞/鼓掌→停止→新消息 | 图片组及原文目标冻结、反应正确；停止边界明确；之后仍可运行 |
| Codex 与 Claude 的续聊、模型/权限设置、压缩、重启 | 原历史与显式配置按能力保留；错误具体，不静默丢会话 |

9. Goal 与 thread.read 的部分真实结果未结算派发；Goal 等待操作在重启后还可能丢失原卡关联。补齐精确原生结果及本人投影持久化，避免查询卡无限等待或无关命令失败干扰正在执行的消息。
10. 只有正常排队输入的重启，被误用旧迁移门禁阻拦；旧附件恢复又因入站时生成的分类字段而校验失败。逐条区分普通已接收输入、已派发输入与旧迁移输入，并从真实认证重连入口验证队列推进；附件保留原消息、正文、文件及目标，不能因恢复而改投其他会话。

升级兼容另行核对：旧存活 wrapper 不一定因 daemon 更新而更换，不能把认证成功等同具备新增回执能力。新能力绑定精确 hello 与连接；旧执行继续保留已有事实，不能盲杀或重放。旧历史会话的 namespace 表示变化与真实未静止执行必须分开处理，不可把两者都隐去，也不能放宽团队或其他用户的历史归属。

旧历史兼容使用迁移来源、目标收据、原生日志和当前历史元数据的完整组合核验。线上三个权威库的只读副本经生产入口核对后，2 条本人业务历史可见、2 条内部控制历史被排除；其中 1 条本人历史满足精确执行器的实时退出／日志检查，另 1 条仍不可续接。准入按所选会话对应的执行器验证，不让无关旧控制记录阻断已经证明安全的历史；也不为恢复体验清除真实未知事实。

线上 `private-chat.db` 的只读备份已用新版实际 `OpenJournal` 从 schema 5 迁移至 7，并逐项恢复其中 checkpoint：1 个 checkpoint、10 个既有效果均保留，没有运行效果或触碰线上库。含派发、关联输入和原生命令的非空旧库另由 schema 迁移测试覆盖，不能把线上这份空 dispatch 样本当作完整迁移证明。

本轮受控验证包括：实际 SDK 菜单／Slash 入口与原卡回调、三个后端设置链、真实 relay／wrapper 与受控原生子进程、原进程跨 daemon 重启后继续下一轮、附件暂存回执跨两次存储重开、认证 hello 后 FIFO 排队推进、原生确认答复乱序，以及先写 resume 再拒绝 compact 的部分写入。完整 `go test ./...`、核心执行六包整包 race、daemon 私聊旅程 race 和 Windows 全仓编译已通过；提交前检查通过，仓库已有跨平台测试路径提醒仍为非阻断提示。
