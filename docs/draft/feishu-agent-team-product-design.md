# 飞书项目群与 Agent 团队产品草案

> Type: `draft`
> Updated: `2026-11-21`
> Summary: 明确完整团队协作目标，纳入多工作流并行、独立执行目录、成果评审与集成，撤回以第一版收缩目标的限制。

## 1. 定位与决策状态

用户在飞书创建项目群，把固定的 AI 同事加入项目；向负责人提出目标，在任务话题中讨论和验收。模型统一管理，项目知识分别积累，同事之间直接协作。

本草案的整体产品方向已获得用户认可，具体数据模型、工具契约和生命周期仍在细化。本文描述目标体验，不代表已实现。技术落点、代码证据、限制与验证步骤见 [技术方案](./feishu-agent-team-technical-design.md)。

目标是完整的 Raft 式角色团队，不以“第一版先缩成独立聊天／串行开发”替代。工程可按依赖顺序推进，角色连续性、并行协作、成果集成与故障恢复均属于交付。源码依据和执行合同见 [完整执行设计](./feishu-agent-team-execution-design.md)。

当前实际行为仍以 [远程面状态机](../general/remote-surface-state-machine.md)、[飞书产品设计](../general/feishu-product-design.md) 和 [卡片状态机](../general/feishu-card-ui-state-machine.md) 为准。本文不将旧群模型标记为已经废弃。

## 2. 核心产品约定

1. 项目有明确负责人和主群；群默认承接一个明确项目，项目身份独立，也可关联其他讨论入口。
2. 一个 Bot 代表一个稳定角色；同一角色可以参加多个项目。
3. 模型、runtime 与基础能力在 Bot 级统一配置，不在每个项目群重复设置。
4. 负责人负责目标、协调、分歧和整体交付；专家之间可以直接提问、交接和评审。
5. 每个领域有明确 owner；小事由对应角色直接完成，大事才拆分协作。
6. 角色保持独立会话；共享需求、决定、任务与成果，不共享全部内部推理或会话。
7. 项目知识与角色通用知识分开；项目局部例外不自动升级为所有项目的规则。
8. 项目身份独立于群、目录和底层会话。更换目录、重建会话不等于删除项目知识。
9. 用户可以只与负责人沟通，也可以随时进入任务话题或直接 @ 专家。
10. 群主消息流展示需求、重要决定、阻塞和交付；详细协作留在任务话题。
11. 独立工作流可以并行，实现、评审和集成都围绕明确版本交接；共享资源冲突只约束相关操作。

## 3. 概念与信息归属

| 概念 | 产品含义 | 管理范围 |
| --- | --- | --- |
| 角色 | 有稳定身份、职责、能力和通用工作方法的同事 | 跨项目复用 |
| 飞书 Bot | 角色在飞书中的稳定可见身份；多个工作会话不产生多个 Bot | Bot 统一配置 |
| 项目 | 长期目标、成员、需求、决定和成果的归属 | 项目独立 |
| 项目群 | 项目的主沟通入口，任务与讨论有明确归属 | 项目级 |
| 项目资源 | 代码仓库或工作资料的来源，可被不同项目关联 | 项目配置，不充当项目身份 |
| 执行目录 | 具体工作流的 checkout/worktree 或工作副本 | 系统按工作管理，不要求用户逐个建目录 |
| 任务 | 有责任人、验收条件、状态、成果和跟进记录的工作 | 项目内 |
| 任务话题 | 任务的公开讨论入口 | 关联任务，不等于 runtime thread |
| 角色通用记忆 | 经提炼的通用方法、长期职责与偏好 | 角色级 |
| 项目资料 | 需求、规范、决定及成果 | 项目内相关角色共同查阅 |
| 角色项目记忆 | 某角色对该项目的经验和工作恢复线索 | 角色 × 项目 |
| 执行会话 | 为具体工作组织上下文并运行底层 agent | 可以结束、恢复或重建 |
| 成果、评审与集成 | 不可变交付版本、对该版本的检查、进入项目目标基线的过程 | 任务与项目共同管理 |

同一个质量 Bot 在项目 A 熟悉移动端弱网，在项目 B 熟悉权限矩阵，同时保持一致的缺陷报告标准。通用能力一致、项目经验不同，是预期体验。

## 4. 场景一：建立第一个项目

### 4.1 一次性准备

管理员先接入负责人、工程师、质量负责人等应用机器人，配置模型和初始职责。初始职责可由自然语言生成，不要求用户手写长提示词。

“给项目添加角色”和“注册飞书应用”是不同操作。角色的飞书身份需完成应用部署；项目邀请负责加入和就绪，不伪装成平台应用注册流程。管理员集中维护 Bot，用户在各项目复用这些同事。

### 4.2 用户操作

1. 在飞书建立普通群，例如“项目 A：客户门户”。
2. 把负责人机器人加入群。
3. 发出“这个群开发客户门户，使用工程师和质量负责人，代码在这个目录”等指令。
4. 负责人整理项目名称、目录、团队和初始资料；缺失内容由选择卡或表单补齐。
5. 用户执行“建立项目”，完成登记并加入选定角色。

项目建立卡展示名称、负责人、团队、项目目录和初始资料，不要求用户理解 instance、surface 或 runtime thread。

### 4.3 系统反馈

- 明确项目是否建立、哪些角色已加入、哪些尚未就绪。
- 已建立项目后，可以直接在群里发需求；负责人承接未指定对象的新事项。
- 提供查看任务、查看团队、查看项目资料的入口，可通过群内菜单重新打开。
- 自动拉 Bot 进群失败时保留建立结果，列出尚未加入的成员及操作入口；不得把部分成功显示为全成功。
- 初始项目登记与首个开发任务分开，避免创建过程中重复派发用户原始需求。

## 5. 场景二：建立另一个项目

用户新建“项目 B：内部管理后台”群，加入同一个负责人，提出“沿用项目 A 的团队，建立新项目并使用新的项目目录”。

“沿用团队”只复用角色选择、统一模型、核心职责和通用工作方法；项目资料、聊天、任务、局部规则及角色项目记忆独立建立。

系统反馈：“项目 B 已建立，沿用相同团队；项目知识与任务独立。”不要求用户重新选择每个角色的模型。

需要复用经验时，用户可以要求“参考项目 A 的验收清单”。系统在已有访问范围内提取适用内容，记录来源，形成项目 B 自己的版本，不默认复制全部项目记忆。

项目可以选择另一仓库，也可以使用同一仓库。系统为独立写工作流管理各自 checkout/worktree，项目上下文和知识仍独立；用户不必通过手动复制目录绕过旧群的目录独占规则。实际可写目录保持明确 owner，仓库来源本身不被某个群独占。

## 6. 场景三：日常开发与协作

用户在项目群提出：“增加批量导出，管理员可以导出全部数据，普通用户只能导出自己的。”

1. 负责人判断是否需要跟踪；普通问答不强制创建任务。
2. 建立任务，记录目标、验收条件、领域 owner 和相关资料。
3. 独立子任务并行实施，质量负责人在指定成果版本上检查；同一角色也可处理多个有独立上下文的工作流，对用户仍是同一个同事。
4. 角色直接提问和交接，公开必要的原因、证据和结果。
5. 需要合入代码的成果由指定集成 owner 处理，冲突有明确修复责任；负责人检查整体目标，向用户交付实际版本与验证结论。

已经明确授权的工作直接推进，不要求用户逐个批准内部拆分。只有影响范围、目标或不可自行决定的取舍才请求用户输入。

复杂任务的子任务可有各自话题并链接到总任务；任务不能靠聊天里的一句“请你做一下”独占表达，系统必须记录责任和状态。

工程师继续修改时，测试结论仍对应之前提交的版本；新成果和新需求不能自动继承旧验收。并行实现不会意味着互相覆盖文件，负责人也不能只收到几句“已完成”就宣布整体交付。

### 6.1 用户反馈规则

| 用户意图 | 操作位置 | 必须产生的反馈与效果 |
| --- | --- | --- |
| 新需求 | 群主消息流 | 默认负责人接手，必要时建任务 |
| 修改需求 | 对应任务话题 | 确认范围变化，更新任务并通知受影响角色 |
| 专家问答 | 相关话题 @ 角色 | 专家直接回答；形成决定时同步任务记录 |
| 界面问题 | 任务话题中的截图与文字 | 关联当前成果及任务，交给相关角色 |
| 查看进度 | 群内提问或任务卡 | 说明责任人、进展、阻塞和需用户决定的事项 |
| 暂停任务 | 任务话题或任务卡 | 明确暂停对象；区分暂停请求与实际停止完成 |
| 继续任务 | 对应任务入口 | 从当前任务事实与待办继续，不重复已完成副作用 |
| 验收交付 | 交付话题或任务卡 | 完成任务，或附修改意见重新推进 |
| 项目规则 | “这个项目以后……” | 保存为项目约定，并告知相关角色 |
| 角色通用规则 | 统一设置或明确“所有项目……” | 展示跨项目影响并更新角色级规则 |

例如用户回复“先只做 CSV，Excel 放下一期”，系统应更新当前范围、后续事项及相关角色的工作依据，不能只回复“好的”。

群里存在多个任务时，“改一下那个”不能按最近发言的 Bot 猜目标；通过关联话题、引用或选择任务明确对象。修改意见不能捕获整个群的下一条消息作为默认输入。

### 6.2 学习与记忆反馈

- “这个按钮大一点”：当前任务的修改意见。
- “本项目主要按钮以后使用这个尺寸”：项目规范。
- “所有项目的缺陷报告都附复现步骤”：角色或团队通用规则。

系统说明记入哪个范围，允许查看、纠正和删除。记忆内容是可修订的经验，不替代任务状态和已确认决定的权威记录。

## 7. 互动入口

| 入口 | 负责的交互 |
| --- | --- |
| 群主消息流 | 新需求、项目级决定、总体进度、重要阻塞 |
| 任务话题 | 讨论、角色交接、截图反馈、成果与验收 |
| 群内菜单与业务卡 | 查看状态、选择任务、暂停继续、打开资料 |
| Bot 私聊或统一设置页 | 模型、核心职责和通用方法等跨项目配置 |

卡片操作必须即时确认受理，业务结果异步更新。长期状态保存在服务端，历史卡片不是永久状态容器；旧入口应可打开当前任务事实。

原有工具执行授权与产品验收保持不同语义：接受交付不隐式同意额外执行权限，工具授权也不代表任务已验收。

## 8. 协作必须满足的行为

1. 接收到团队信息，不代表每个角色都需要发言；明确指派和自己负责的变化才产生行动。
2. 对方忙碌时交接进入待办，不因群并发限制直接丢失。
3. 等待同事的角色结束当前执行并释放执行资源，结果到达后再被唤醒。
4. 成果、任务和决定有稳定引用；角色可以补读，避免只依赖一段转述摘要。
5. 过程只公开关键协作与可验证结果，不持续转发全部工具日志和内部推理。
6. 有明确完成、阻塞、暂停和取消状态；不会靠无限互相 @ 保持运行。
7. 人的消息、角色协作消息与系统事件保留来源，角色不继承群内人的管理权限。

## 9. 飞书能力与适配边界

官方平台支持应用机器人收发消息、把已有机器人拉进群、话题回复、历史读取及卡片交互。权限尚未开启不是本轮可行性研究的阻塞；上线时仍需完成授权和应用发布。

- 其他 Bot 的 @ 消息与普通群消息分别有专门接收权限；当前应用清单已有前者。
- 普通群可以使用话题回复；读取群历史只得到话题根消息时，需要再读取话题历史。
- 群成员设置会影响自动邀请；目标角色必须已经是可用的应用机器人。
- 卡片回调应先响应，长任务异步完成；卡片有更新和生命周期限制。
- 同一系统管理的角色可以在内部可靠交接，并将公开协作投影到飞书；不能同时把回显再次当成新的交接执行。

## 10. 完整目标验收场景

1. 建立两个项目，使用同一批角色和统一模型，项目资料与任务独立。
2. 在项目 A 提出需求，负责人委派，专家完成一次直接交流，检查后交付。
3. 中途修改需求，相关角色使用最新要求；项目 B 不受项目 A 局部规则影响。
4. 目标角色忙碌或运行服务重启后，交接仍存在且能继续。
5. 重建底层会话后，角色知道职责、当前项目及待办；更换模型不重建角色身份。
6. 在任务话题回复或发图能够找到正确任务，不误投其他任务或项目。
7. 用户暂停时能看到实际状态；恢复后不重复已经成功执行的外部操作。
8. 两个角色同时实施独立任务，第三个角色可讨论和评审；同一角色多个明确工作流的输出不串任务。
9. 不同项目关联同一仓库，工作目录与记忆互不混用；合入同一目标分支时有清晰的基线与冲突处理。
10. 评审期间实现继续前进、需求改变或集成基线更新时，不把旧的通过结论套用到新成果。
11. 工作中收到新消息、压缩上下文、重建会话、换模型和服务重启，都保持任务与角色连续性。
12. 用户在编辑器接管工作后自动调度不争抢同一会话，归还后团队能从实际进展继续。

## 11. Raft 参考与适配选择

Raft 强调稳定角色、按领域承担责任、公共讨论、任务与成果，以及角色自己的持久记忆。它不强制所有通信经过最高负责人。

Raft 的 Server 是团队归属，Channel 是讨论范围，Agent Workspace 是角色自己的持久资料目录。本文将项目知识显式划分，并保留按项目运行会话，是针对当前飞书产品的适配，不声称 Raft 默认按每个 Channel 创建完全隔离的角色记忆。

Raft 源码证实个人工作目录、原生 Agent 生命周期、忙碌消息投递与团队并行；尚未证实它自动为每个任务创建 worktree 并合并。本文的执行目录与集成合同是我们自己的完整设计，不以未证实的 Raft Git 自动化作为依据。
