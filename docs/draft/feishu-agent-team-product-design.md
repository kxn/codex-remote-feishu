# 飞书中的 Raft 式 Agent 团队：完整产品设计

> Type: `draft`
> Updated: `2026-11-21`
> Summary: 完整定义群协作、单聊、Agent 自主管理 Git、会话 Goal，以及团队／项目资料的稳定维护和版本边界，弃用旧 Cron。

## 1. 产品定位与设计依据

用户在飞书项目群与一组固定 AI 同事工作：平时向负责人描述需求，负责人组织分工，专家直接交流、并行实施和互审，最后给出可验证成果。用户能够随时指导、改变范围、暂停或验收；无需手动创建原生会话、worktree 或管理上下文窗口。

**最高优先级是 Raft 式群工作体验。** 单聊是同一位同事的私人工作入口，使用相同的记忆和运行机制；不能为了兼容旧单聊／群菜单而保留另一套薄包装内核。旧群体验可整体替换，旧 Cron 产品与实现不继承。

本设计按已核查的代码、Raft 机制和飞书 API 能力形成。资料接口、身份限制及明确替代路径见 [共享资料接线](./feishu-agent-team-materials-design.md)，运行机制见 [执行设计](./feishu-agent-team-execution-design.md)，整体改造见 [技术设计](./feishu-agent-team-technical-design.md) 和 [代码审计](./feishu-agent-codebase-reuse-assessment.md)。这些是目标合同，尚未实现，不把接口可行性当端到端验收。

交付包括稳定角色、并行协作、持久待办、分层记忆、共享资料、版本评审、恢复和迁移。不以“先做多个 Bot 独立聊天”“先串行共享目录”替代完整目标；实现顺序只表达依赖。

## 2. 人、Agent 与系统分别做什么

| 参与者 | 主要职责 |
| --- | --- |
| 人 | 提出工作、决定范围和重要取舍、选择真实资源、验收；随时暂停／取消／接管 |
| 负责人角色 | 理解需求、组织计划和责任、协调依赖与分歧、检查整体交付；不垄断专家通信 |
| 专家角色 | 在职责内自主实施、向其他同事提问、交接、评审；维护自己的工作检查点 |
| 运行系统 | 确保消息和待办不丢、会话与身份不串、恢复可追溯；维护资料引用、版本和外部操作回执 |

模型／provider 和已有工作目录／仓库保留精确选择器。用户已给出明确选择时直接采用；信息不明确时让用户选真实对象，不让 Agent 猜选哪个已有目录。Agent 可解释选择影响，但不自行更换统一模型。

用户选定资源后，Agent 通过原生 shell／Git 自主管理分支、checkout、worktree、冲突修复和清理。系统记录继续工作所需的执行位置与成果，**不另造 worktree 创建／回收／自动合并引擎**。对用户展示的是工作进展和结果，无需填写内部路径或理解 Git worktree。

原生会话绑定、上下文压缩、检查点和重建由运行层处理。菜单不再逐项搬运旧的 instance/thread、compact、autowhip、cron、primary 等技术操作；必要诊断和接管仍可查。

## 3. 产品概念与范围

| 概念 | 含义与边界 |
| --- | --- |
| 角色／Bot | 稳定 AI 同事及其飞书身份；可加入多个项目；职责与通用方法可维护 |
| 团队 | 复用的同事组合和共享资料范围；独立于一个群，不自动等于整个企业租户 |
| 项目 | 有长期方向、成员、任务、资源、决定及成果的工作范围；独立于目录和原生会话 |
| 项目群 | 项目主沟通入口；默认一个明确项目，可关联其他讨论入口 |
| 任务 | 有责任人、范围、验收、依赖及成果的工作；普通问答不强制建任务 |
| 任务话题 | 公开讨论和反馈入口；不等于底层 runtime thread |
| 项目资源 | 人明确选定的仓库、既有目录、文档或资料空间；可以被多个项目关联 |
| 执行位置 | Agent 实际工作的目录；可随工作调整，不充当项目身份或永久资料库 |
| 共享资料 | 人与团队共同维护的原文、数据、规范和资料索引，有稳定入口与来源 |
| 记忆 | 角色方法、个人偏好、项目经验、恢复线索；引用资料，不能替代权威原文 |
| 成果版本 | 本次交付固定的 commit、文档／表格快照或文件版本；与当前资料链接并存 |
| 会话持续执行目标（Goal） | 帮助原生 Agent 持续推进当前工作、防止提前停下或偏离；不是项目目标，也不是验收结论 |

同一 Bot 的 backend/model/profile 统一配置，项目不重复选一遍；具体会话的执行宿主、人工接管和已生效配置分别记录。换模型保留角色身份和记忆，不等于立刻重启所有正在工作的项目。

同一个质量负责人在项目 A 熟悉移动端弱网，在项目 B 熟悉权限矩阵，同时使用一致的缺陷报告方法。角色通用知识、团队规范、项目资料、角色项目经验、个人私聊记忆分别归属；不能因为复用角色就共享全部聊天和项目历史。

## 4. 一次性准备与建立第一个项目

### 4.1 准备同事与团队资料

管理员接入可用飞书 Bot，选择各自模型／provider 并描述职责，例如“你负责质量，重视可复现证据和边界条件”。角色说明可由自然语言整理，不要求人手写长预制提示词；后续指导有明确作用范围，不能靠任意聊天自动改变全局职责。

创建或选择一支团队，配置负责人和可用专家，指定团队资料入口。有 Wiki 时选已有空间／父节点；没有时系统建立应用管理的固定资料首页及云空间目录。不是每个项目都必须让用户先建 Wiki 空间。团队资料默认作为项目可引用资源，不复制成每个 Bot 的文件。

添加现有角色与注册飞书应用不同：应用身份仍需管理员部署；Agent 能把已配置角色加入项目，不能伪称自动完成应用注册和发布。

### 4.2 用户建立项目

1. 用户新建“客户门户”群，将负责人加入群，说“这个群做客户门户，用工程师和质量负责人”。
2. 负责人整理项目名称、团队、初始需求，询问确实缺少的资料；需要开发代码时用户明确指定或选择已有目录／仓库。
3. 项目建立卡只显示业务选择：项目、团队与负责人、仓库／目录、资料位置、是否接入已有 issue 流程。明确指令已包含建立授权时直接执行，卡用于补齐遗漏和展示结果，不增加重复确认。
4. 系统登记项目、邀请选定角色、建立固定项目资料首页，关联团队规范及已有需求资料。
5. 群里反馈项目已建立、哪些同事已就绪、哪些操作仍待完成，并提供“工作”“团队”“资料”的固定入口。

没有代码的研究、策划或资料工作可以不选仓库。以后开始开发时再明确关联真实资源；不为了创建群项目强迫填写代码路径。

项目登记与首个开发任务分开，避免创建时把同一条需求派发两遍。部分成员加入或资料建立失败时保留已完成部分，显示具体状态并恢复重试；不能把半成品显示成全部就绪。

### 4.3 用户看到的项目资料首页

首页固定链接，包含项目说明、已确认的主要决定、任务／issue 入口、成果、业务资料、repo 文档入口及团队规范引用。内容随工作更新，不每天产生新首页，也不默认生成大量空白模板。

Wiki 是可选导航容器。资料本身可以来自 Docx、Bitable、Sheets、repo 或外部链接，首页汇总这些来源，不将其复制成一套可独立改写的正文。

## 5. 建立另一个项目

用户新建“内部后台”群，加入同一负责人，说“沿用客户门户的团队，建立另一个项目”。负责人复用同事及团队资料，用户选择这个项目的真实仓库／目录和必要初始资料。

系统明确反馈：团队沿用，项目任务、决定、资料及角色项目记忆独立建立。同一 Bot 继续用统一模型，不要求每群再设一遍。

两个项目可以关联同一仓库；Agent 自主组织独立写工作位置，运行层不会再按群独占整个仓库。项目之间的代码关联不等于记忆混合。

“参考项目 A 的验收清单”是在访问范围内引用来源或提取适用部分建立 B 的版本，不复制 A 的全部项目记忆。团队规范默认引用同一个原件；项目特殊规则单独记录，并明确覆盖哪条通用规则。

## 6. 日常群协作

### 6.1 提需求、实施与交付

用户说：“增加批量导出，管理员能导出全部，普通用户只能导出自己的。”

1. 负责人理解范围，读取相关项目资料；需要跟踪时建立任务，写清验收和责任。普通解释问答直接回答。
2. 若项目接入工程 issue 工作流，创建或关联 issue，任务话题链接 issue 及采纳的资料版本；不建立另一份可独立改写的需求正文。
3. 负责人安排实现和测试，专家直接交流。独立工作并行，代码隔离与 Git 操作由 Agent 自主完成。
4. 实现者提交具体 commit／PR，质量负责人检查指定版本。资料任务则提交固定文档／数据版本。
5. 指定角色完成集成与必要验证，负责人核对整体要求，向用户交付成果、证据和仍需决定的事项。

同一角色可以参与多个工作流，对用户仍是同一个同事；消息、成果及恢复线索不会串任务。负责人无需等待所有同事完成才能接收新要求。

“已完成”要有成果和对应证据。新提交不能自动继承旧测试结论；需求修订也不能自动继承旧验收。任务是否需要集成或人验收按工作约定决定，不给普通问答套完整工程流程。

### 6.2 用户如何反馈

| 意图 | 入口 | 反馈与结果 |
| --- | --- | --- |
| 新需求 | 群主消息流 | 负责人承接，说明是否已建工作项及范围 |
| 修改要求 | 对应话题、引用消息或任务卡 | 明确目标事项，记录修订并通知相关角色 |
| 问专家 | 话题中 @ 同事 | 专家直接答复；形成决定时写回权威记录 |
| 截图反馈 | 相关话题 | 关联任务和成果版本，进入修复工作 |
| 查看进展 | 群里询问或“工作”入口 | 显示责任、进展、阻塞、成果及需人决定的内容 |
| 暂停／取消 | 话题、卡片或明确指令 | 先确认受理，再显示实际停止；未确认停止不冒充已经停下 |
| 继续 | 原任务入口 | 使用当前事实和未处理输入继续，不盲目重复外部操作 |
| 验收／返工 | 交付话题或卡片 | 对指定成果验收，或记录修改意见并推进 |

已授权的工作直接推进，不逐项要求人批准内部拆分。含糊的“改一下那个”通过引用或选择任务澄清，不按最后发言 Bot 猜测，也不捕获群里无关的下一条消息。

例如“先只做 CSV，Excel 后面再做”应更新当前范围和后续事项，通知实现与测试；不能只回复“好的”。若 issue 是本项权威记录，更新成功后才显示范围已同步，外部暂时失败则明确待同步。

### 6.3 消息与等待

群主流展示需求、关键决定、阻塞和交付；详细交流在任务话题。专家之间能直接交接，负责人可以检查和指导，不需要所有消息都经它转述。

角色忙碌时消息进入持久待办；等待同事时释放模型执行资源，结果到达后继续。服务重启仍能恢复，不要求人再说一句“继续”。不以循环互相 @、固定重复提示或 sleep 保持工作。

公开的是必要的协作证据，不持续倾倒工具日志或内部推理。后台的可靠交接投影到群，飞书回显不会被当成第二次委派。

## 7. 团队与项目资料的完整体验

### 7.1 资料放在哪里

| 用户内容 | 默认位置 | 规则 |
| --- | --- | --- |
| 团队通用标准、方法、术语 | 团队 Docx／知识库 | 多项目引用同一资料，不各自复制 |
| 项目产品说明、背景、用户流程、会议决定 | 项目 Docx | 原位持续维护；已采纳要求记录对应版本 |
| 工程事项的范围、验收、业务状态 | issue；未接入 issue 则内部任务 | 单项只有一个权威工作记录 |
| 代码变更、代码审查、CI 和合并 | PR／Git | 群与表只展示关联和结果，不自造“已合并” |
| 跟代码版本变化的架构、接口、部署与仓库规范 | repo docs | 随代码提交和评审；飞书提供链接／标明版本的只读预览 |
| 用例库、业务台账、资料目录 | Bitable | 区分人工字段、系统字段、外部状态投影 |
| 公式计算、预算分析、比较矩阵 | Sheets | 精确更新目标范围，保留公式、输入和来源 |
| 图片、文件、报告 | 永久资料／制品存储 | 资料目录登记；临时消息附件用于分发 |

用户不必先学习这张表再开始：负责人根据内容采用默认位置，首次建立时说明去向。用户可明确指定已有资料。Agent 不为每次回复重新建一篇文档，也不把所有材料都塞入 issue 或代码仓库。

一项资料一个权威原件；跨位置通过链接、引用、标版本的预览连接。PRD 说明整体行为，issue 记录本项采纳范围；repo 中最终技术契约随代码生效，不与飞书另一份技术正文双向自由改写。

### 7.2 更新、共同编辑与版本

用户说“把导出权限补进需求说明”，Agent 找到原资料并更新同一文档，反馈修改摘要和原链接。人在飞书中继续编辑，角色后续读取最新资料，并知道当前工作采纳的是哪个版本。

在线文档的编辑不自动等于项目批准新需求。修改影响活动任务时，负责人说明差异；已明确的用户变更直接修订任务，尚未确认的草稿作为建议，不静默改掉正在执行的目标。

多人共同编辑时，Agent 只更新相关段落、记录或单元格；不整篇覆盖。冲突时展示差异或修改建议，整合后继续。系统不能保证飞书 API 提供它实际没有的强并发锁；强保留人工内容的区域采用建议后采纳方式。

“查看当前资料”打开固定入口；“查看当时交付”打开当次固定版本。里程碑和验收保存可复核快照，包含来源、内容及相关附件，不只保存一个会变化的链接。飞书可读命名版本是辅助，不代替版本清单和必要持久快照。表格无法保证同一源版本读取时，明确交付的是注明采集范围与时间的固定数据集；需要严格同版的验收须先形成可核实基线，不把多次读取假装成原子快照。

### 7.3 表格怎样参与工作

Bitable 可以管理用例库、需求收集或资源台账，但不会取代内部可靠运行队列。工程 issue 的状态可投影到表格；用户通过“暂停／修改要求”等明确业务操作影响任务，不能随手改一个展示单元格便伪造合并或完成。

Sheets 用于计算和分析。业务字段可由人编辑，公式区域和系统生成字段明确区分；Agent 读写指定范围。交付分析时记录输入、公式和结果，而非只有一张截图。

资料目录的行引用原件，不存第二份全文；重复维护同一资料更新同一行。项目无需同时启用 Docx、Wiki、Bitable 和 Sheets，按实际资料类型使用。

### 7.4 查找、失联与归档

用户在群里问“最新验收规范在哪”或打开“资料”，得到可访问的原件、用途、版本及更新时间。Agent 按需读详细内容，不在每轮提示词中塞全部资料。

访问失效或源文档被删时明确显示不可用；有缓存也标明时间和版本，不把旧摘要冒充最新。换模型、重建会话、清理 worktree、退出群都不删除长期资料。

项目归档保留资料及成果沿革，取消项目对团队资料的引用不删除团队原件。永久删除是独立的明确动作，需处理关联引用、快照及索引；不与清理临时执行文件混在一起。

## 8. 记忆、规则与会话 Goal

### 8.1 记忆的范围与反馈

- “按钮再大一点”：本项修改意见。
- “本项目主要按钮都用这个尺寸”：项目规范，维护项目资料并通知相关角色。
- “团队所有缺陷都附复现步骤”：团队通用规范，影响引用它的项目。
- “你以后做检查都先核对边界条件”：角色通用方法；涉及跨项目变化时明确说明范围。

系统告知写入范围，用户可查看、纠正和删除。资料原文是知识依据，记忆是摘要、经验和恢复入口；原文更新后旧摘要失效，不能让模型一直遵守过期笔记。个人偏好不自动提升为团队规范。

### 8.2 Goal 的位置

会话 Goal 放在工作详情中的“持续执行”状态，服务于当前工作不断档；不作为项目导航中的“项目目标”，也不要求用户为了每个任务手动设置一次。

项目目标回答“这个项目要做成什么”，任务要求回答“这项工作怎样算完成”，会话 Goal 帮助底层 Agent 把当前工作继续做完。会话完成信号不代表项目验收；模型自行改写自己的 Goal 也不能反向更改用户要求。

支持原生 Goal 的 backend 使用其能力；当前仓库只实现 Codex headless 的 Goal 接入，不能声称 Claude 已有等价接口。其他 backend 由相同工作事实和持续执行策略承接。暂停、修改范围和重建会话同步处理 Goal，避免旧目标继续运行或两个机制重复催促。

## 9. 单聊体验

用户直接找某位同事讨论、做事、指导或继续过去工作。默认个人范围，保留个人偏好和工作检查点；普通聊天不强迫创建项目或任务卡。

明确选择／提到某项目后，同事读取该项目可访问资料，界面说明当前范围。私聊内容不自动发到群；需要公开任务、决定或资料时，按用户明确意图或已授予的协作范围写入项目，并反馈去向。范围不明时选择项目，不按最近活跃群猜。

私人资料默认留在个人集合；“把这份整理分享给项目 A”建立明确共享版本／关联，不能自动公开整段私人对话。团队资料可在授权范围内查阅，但复用同一个 Bot 不赋予跨用户个人资料访问权。

单聊保留精确模型／已有资源选择，以及停止、继续和接管能力；去掉要求人手动维护底层会话的步骤。开始新话题不清空长期记忆，重建模型会话也不等于丢失工作。

## 10. 入口与状态反馈

| 入口 | 用户能做什么 |
| --- | --- |
| 群主消息流 | 提需求、看总体进展、处理关键决定和阻塞 |
| 任务话题 | 与负责人／专家交流、反馈、查看成果与验收 |
| 工作入口／任务卡 | 看责任和状态，暂停、继续、取消，打开 issue／PR 和当次成果 |
| 团队入口 | 看角色职责与成员，添加已配置同事，打开团队资料 |
| 资料入口 | 看固定项目首页，添加现有资料，查当前／历史版本和来源 |
| 当前选择／工作详情 | 精确选择已有资源，查看作用范围；必要时查看持续执行预算及接管 |
| Bot 私聊／统一管理 | 模型／provider、角色通用方法、凭据与管理政策 |

卡片先反馈已受理，长操作异步更新；旧卡打开当前事实，不能沿用过期 revision 修改新工作。业务验收、工具执行授权和模型设置是不同语义，不能互相隐式代替。

状态用用户能理解的语言：待处理、进行中、等同事／用户、待验收、完成、取消，暂停单独说明是否已实际停下。资料操作显示已更新、待同步、部分完成或冲突；不把“已发出请求”显示成“已经完成”。

菜单的职责是明确对象、准确选择和直接控制。旧命令列表不是必须保留的功能清单；原生技术详情只在诊断和主动接管时出现。

## 11. 飞书适配与实现边界

飞书支持 Bot 消息、邀请已有 Bot、话题回复、历史读取及卡片交互；团队内部可靠交接与飞书公开展示并存。群、话题和消息不是持久任务数据库。Bot 互相接收消息需要对应平台能力，应用配置不足给出具体状态，不缩减团队设计。

Docx、Sheets、Bitable 的应用身份接口支持本设计中的资料读写。纯 Bot 不能创建 Wiki 空间，因此用户选已有空间，或使用固定资料首页／云空间目录；不要求因此引入强制 User OAuth。细节与官方证据见 [接线矩阵](./feishu-agent-team-materials-design.md#2-已核实的-api-接线)。

文档和表格的并发保护、事件覆盖与历史能力有平台限制。实现采用写入协调、局部更新、回读、变更建议、持久版本及补读，不承诺自动无损双向同步所有载体。

Agent 自主管理 Git 不等于 shell 不会出错：负责人协调责任，系统防止已知执行绑定冲突、记录成果与恢复位置，但不声称这些记录能禁止所有外部文件操作。发现冲突或位置丢失时由 Agent 核查修复，不偷偷覆盖用户文件。

旧 Cron 完全退出本次产品，旧计划不自动迁为新工作。未来确需定时业务时重新设计；依赖完成、消息到达、故障重试和资料刷新属于当前运行机制，不需要先复活 Cron。

## 12. 迁移与完整验收

保留 Bot 凭据、用户真实目录、已有有价值的资料和历史关联；旧群 UX、旧人工 worktree 流程、旧 Cron 无需兼容。迁移暂停旧触发与在途执行冲突，保留旧计划只读历史，不继续其后台清理行为。

已有临时上传资料按使用价值和明确来源登记为长期资料，先核实已脱离预览清理范围，再告知保存完成。不能承诺旧临时 URL 永久有效；发生迁移时给出新固定入口和来源沿革。repo 文档保持 Git 权威。

完成产品需要通过以下场景：

1. 同一团队建立两个项目，使用统一角色／模型，项目知识独立，团队资料引用同一原件。
2. 负责人分解需求，专家直接交流，并行实施和评审，指定角色完成集成，负责人交付可验证版本。
3. 用户选择已有目录后，Agent 自主管理 Git；不要求人建 worktree、选原生 thread 或手动 compact。
4. 需求改变，相关工作修订并获得新依据；旧成果／评审不伪装成已符合新要求。
5. 忙碌、等待、断连、服务重启、压缩和会话重建不丢待办，恢复不重复已证实的副作用。
6. 同 Bot 的多个私聊和项目同时工作，作用范围、消息、资料和记忆不串线；人工接管不与自动调度争抢。
7. 同一文档更新多次仍是同一当前链接，历史交付能查看固定内容；人工编辑冲突有明确整合路径。
8. 团队规范更新可通知引用项目；项目特殊规则不会改全团队；个人资料不能未经明确共享就公开。
9. issue／PR、repo 文档、飞书资料有唯一事实来源；表格改动不伪造代码合并，PRD 草稿改动不偷偷改执行目标。
10. 资料失联、创建回执丢失、部分写入、事件遗漏、异步版本未完成都有真实反馈与恢复，不能靠反复新建副本规避。
11. 暂停实际停止，会话 Goal 不绕过控制；其完成不自动判项目验收。旧 Cron 不继续触发。
12. 项目归档、会话重建和 worktree 清理不删除共享资料；解除引用不会误删其他项目的原件。

## 13. Raft 参考与本产品适配

Raft 强调稳定角色、领域责任、公共交流、任务成果及持久记忆，不强制所有通信经过最高负责人。其 Server 是团队归属，Channel 是讨论范围，Agent Workspace 是角色持久资料目录，并不等于全团队共用的代码 checkout。

本产品显式增加项目范围、单聊个人范围、飞书资料与仓库的权威边界；不声称 Raft 为每个 Channel 自动隔离全部记忆，也没有足够源码证据证明它自动为每任务创建和合并 worktree。Agent 原生 Git 自主管理是本产品选择，不以未核实的 Raft 特性作依据。
