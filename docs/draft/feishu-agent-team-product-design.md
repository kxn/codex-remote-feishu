# 飞书 Agent 团队产品设计：用户旅程、交互与验收

> Type: `draft`
> Updated: `2026-11-21`
> Summary: 将团队产品展开为 30 个用户故事，定义界面内容、正常与异常路径、状态反馈和可追踪 UAT；与技术主文档共同作为实施入口。

## 1. 阅读方式与产品合同

本文是目标产品的唯一体验规范，[技术设计](./feishu-agent-team-technical-design.md) 是实现合同。两者尚未实现，不把现有接口或单元测试当作新产品已交付。专项文档用于核对源码、平台限制和细部协议；出现表述歧义时先按本文确认用户行为，再按技术主文档修订实现合同，不能各选一份实现。

故事编号 `US-01`—`US-30` 是需求和实现追踪键；验收编号 `UAT-01`—`UAT-60` 定义可观察结果。文中的按钮文字是产品语义基线，卡片排版可按飞书限制调整，不可省略作用对象、真实状态与异常出口。示例项目名、角色名和交付工具不是强制模板。

最高优先级：用户在飞书群里与一支持续工作的 AI 团队合作，平时主要和负责人沟通；负责人组织工作、分派、检查与指导，专家可以直接交流和并行工作。人管理方向和自己的注意力，不管理原生会话、上下文窗口或 worktree。

完整交付包括：角色复用、跨项目隔离、持久协作与记忆、并行执行、共享资料、版本反馈、自然语言委托、恢复、原有单聊能力迁移。工程分阶段只能表达依赖，不能把其中一部分当成缩小后的产品终点。

### 1.1 已确定的取舍

| 固定产品规则 | 项目／用户自行决定的内容 |
| --- | --- |
| 工作、身份、执行、资料各有稳定归属，接收／执行／发布／送达状态真实 | 做什么项目、怎样拆分、是否使用 issue、何时算业务完成 |
| 主群概要、话题细节、固定资料入口；人能绕过模型停止工作 | 哪些事项要人看、评审强度、交付到本地修改／commit／PR／合并／部署哪一步 |
| 群退出旧 Slash 工作流；私聊保留适用命令并迁移到统一内核 | 项目采用哪些工程方法，阶段之间如何调整 |
| 模型与既有目录／仓库由人明确选择；Agent 管理内部 Git 工作位置 | 新项目引用哪些团队规范、在哪个已有资源上开展工作 |
| 记忆不替代资料原文；声明固定版本时必须有固定依据 | 普通结论、当前页面走查、摘要还是可复现固定版本交付 |
| 旧 Cron 退役；会话 Goal 不当项目目标 | 未来是否另行设计定时业务产品，本次不沿用旧 Cron |

产品提供好用的默认方法库，不强制统一工程流水线。已明确授权直接执行；只有缺失信息会改变资源、公开范围或决策责任时才询问，不把每条任务变成填写流程表。

### 1.2 概念和用户认知

| 概念 | 用户理解 | 不等同于 |
| --- | --- | --- |
| 同事／角色 | 有固定职责、模型配置和飞书 Bot 身份的 AI 同事 | 一次聊天或模型名称 |
| 团队 | 可复用的同事组合、方法和共享资料范围 | 企业全体成员或某一个群 |
| 项目 | 有自己要求、决定、工作和资料的长期工作范围 | 群 ID、目录或原生会话 |
| 项目群 | 当前项目主入口；可以关联补充讨论群 | 项目的唯一数据存储 |
| 工作项／任务 | 需要持续跟踪的工作、责任和结果 | 每条消息；普通问答可直接结束 |
| 任务话题 | 围绕某项工作的公开讨论位置 | Codex thread 或 Claude session |
| 个人工作 | 人与某位同事的私聊工作连续性 | 自动共享给同事参加过的所有项目 |
| 资料与成果 | 持续维护的原件、当前链接或明确版本 | 临时上传缓存与全部执行日志 |
| 记忆 | 有来源、可纠正的偏好、经验与恢复线索 | 隐藏的第二套需求文档 |

同一同事可以同时在项目 A、项目 B 和个人私聊工作；项目经验各自积累，通用职责与明确共享的方法复用。一个原生执行会话不跨这些范围借用。换模型保留同事身份与长期记忆，不承诺沿用另一 backend 的原生历史格式。

## 2. 用户入口、屏幕内容与反馈规则

### 2.1 不需要额外门户的主要入口

| 入口 | 固定可见内容 | 可执行动作 |
| --- | --- | --- |
| 群主消息流 | 新需求的承接、关键变化、合并后的阻塞、交付摘要 | 直接说需求、改变参与约定、询问进展；@ 专家 |
| 任务话题 | 任务摘要卡、相关讨论、变化、当前成果 | 补充要求、截图反馈、查看工作、暂停／继续／取消 |
| 群“项目”文档 Tab | 固定项目首页，链接同一份资料 | 查看项目概况、公开待处理事项、当前成果、资料、工作入口 |
| 导航消息及置顶／Pin | 项目名称、负责人、首页链接、“查看工作”“暂停项目”操作卡入口 | 找回项目入口；停止控制不依赖负责人回复 |
| 工作卡／工作列表卡 | 标题、责任同事、状态、最近实质进展、阻塞原因、结果链接 | 查看详情、限定目标的暂停／继续／取消；按需选择具体工作 |
| 人的决定卡 | 需要决定什么、为何需要此人、建议、影响、相关对象 | 明确选择、提出修改、转交负责人；旧卡打开最新事项 |
| Bot 单聊与管理入口 | 当前个人／项目范围、适用 Slash／菜单、明确配置控件 | 个人工作、选择已有资源／模型、查看记忆、手动运行控制 |

项目首页是同一事实的索引：依次显示项目说明和负责人、当前公开待处理事项、进行中的主要工作、最新成果、资料来源、更新状态。空栏目不生成空文档；完整工作历史通过工作入口展开。首页更新失败标“索引待更新”，群任务记录仍可使用。不能让 Agent 直接改首页状态文字来改变真实任务。

主群不广播每次工具调用或内部思考。内部交接要可追溯，默认公开任务责任、实质结论和需要协作的变化；详细工具过程留在执行记录，用户主动查看时提供必要证据。不同事项分别归入自己的话题，不每次回复新建一个话题。

### 2.2 卡片与长操作的共同合同

- 操作先返回“已受理／已记录”，只有实际完成后才显示完成；处理中显示对象和动作，例如“正在暂停：批量导出”，不能只显示一个无对象的转圈。
- 重复点击返回同一操作；卡片过期提示“此事项已变化”，给当前状态和新入口，不静默执行旧选择。
- 按钮提交、自然语言和私聊命令调用相同业务动作。卡片不是任务本身，消息删除也不删除工作。
- 反馈框只接收该操作者针对该事项的内容；不捕获群下一条无关消息。文本、图片、引用消息都保留来源。
- 无法继续时说明：已完成什么、卡在哪里、现在是否还在运行、由谁处理、用户可做什么。技术日志按需展开，默认不给人内部栈追踪。
- “保存成功”“发布成功”“消息已发送”“人已决定”分别显示。飞书发送回执不称作人已读；产品没有可靠已读证据时不展示已读。

### 2.3 用户看见的状态

| 对象 | 状态与含义 | 离开状态的动作 |
| --- | --- | --- |
| 项目 | 建立中、可工作、部分能力待恢复、暂停中／已暂停、归档中／已归档 | 完成建立步骤、恢复能力、明确继续或重新打开 |
| 同事 | 加入中、可用、忙碌、暂不可用、已退出 | 平台加入和执行准备分别确认；忙碌仍能接待办 |
| 工作 | 待处理、进行中、等待同事／人／资源、待检查、完成、取消 | 有实际进展、依赖回信或明确业务决定；待检查按项目需要出现 |
| 运行控制 | 暂停请求已受理、停止确认中、已暂停、停止状态待核查 | 原生运行结束证据或检查结果；不能凭超时称作已停止 |
| 资料 | 草稿、已发布／已更新、待同步、冲突、源不可用、已归档 | 更新回执、处理冲突、恢复来源；可用缓存标明时间 |

工作状态和执行状态同时成立：例如“等待你决定，模型已空闲”“工作取消，运行停止待核查”。取消不会撤回已经发送的消息、已合并代码或已发布文档；需要撤销这些副作用时单独处理。

## 3. 建立团队与项目

### US-01 配置可复用的 AI 同事

**作为团队组织者，我希望接入已有 Bot、选择模型并描述职责，让以后每个项目直接使用同一位同事。**

前提：管理员已接入飞书应用及可用执行宿主。应用注册、发布和凭据部署属于系统接入；不是聊天里凭空创建应用。

正常流程：进入同事管理 → 选已接入 Bot → 用现有选择器选 backend/profile/model → 填一句职责或在私聊描述 → 系统保存角色并显示“适用于该同事参加的所有项目”。负责人和专家都用此对象。职责可以由 Agent 帮忙整理，人不需要写完整提示词。配置有明确来源与版本。

继续指导时，“在这个项目重点检查弱网”只写项目经验；“以后所有项目都按这个方法检查”才进入角色通用规则。系统简短反馈保存范围，不把普通聊天悄悄训练成全局人设。

异常：Bot 绑定变更保留角色历史，但新身份未核对前不能继续旧调用；模型暂不可用显示同事暂不可用，待办保留，不擅自换另一个模型。职责表达有会改变跨项目范围的歧义时只澄清该点。

验收：UAT-01、02、42。技术：T02、T06、T09。

### US-02 组成团队与共享方法

**作为组织者，我希望指定负责人和可用专家，复用团队资料与工作方法。**

创建团队时选择已有角色，指定一位默认负责人；可以仅有负责人，后续增加专家。选已有团队资料入口，或者使用系统管理的 Drive 资料根及固定 Docx 首页。Wiki 可关联已有空间／父节点，不要求先开新空间。团队不是租户全部成员的隐式共享范围。

内置方法库直接可用，无需逐个勾选。用户可以说“我们团队缺陷都附复现步骤”，维护团队规范并展示影响范围；引用它的项目在新工作或明确变更处理后采用，不能偷偷改写进行中的要求。

异常：资料入口不可写时团队仍可登记和交流，显示“团队资料待连接”；依赖该资料的工作等待，其他工作可开展。负责人不可用时可由有权用户明确更换；系统不自行把模型配置最高的同事当新负责人。

验收：UAT-03、04。技术：T02、T09、T10。

### US-03 在新群建立第一个项目

**作为项目发起人，我希望把一个普通飞书群变成团队工作入口，并立即开始第一项工作。**

示例：“这个群做客户门户，用工程师和质量负责人，沿用产品团队。”

1. 负责人读取当前群是否已有项目绑定，识别名称、团队和要求；已有明确授权直接建立，不另加“确认创建吗”。
2. 缺少真实资源时发一张补充选择卡：项目名、团队／负责人、已有仓库／目录、资料位置。已明确字段只显示，不重复提问。非代码项目允许“不需要代码资源”。
3. 系统先登记项目，再邀请选定角色、建立固定首页、建立原生群入口；每一步显示独立结果。
4. 建立结果示例：“客户门户已建立。工程师已加入；质量负责人加入中。项目资料已就绪。”附首页和工作卡入口。需要质量检查的工作等该角色就绪，其他已具备条件的工作可运行。
5. 同一条建项目消息包含的首个需求只登记一次，建立步骤完成后继续承接，不要求用户再发一次。

异常：重复创建返回既有项目；若群已属于另一项目，展示已有绑定，只有用户明确换项目才启动切换。邀请超时先核实是否已入群；首页创建结果未知先对账，不能重试出多份首页。用户在建立过程中改目录，后续采用新选择，旧异步结果不得覆盖。

验收：UAT-05—08。技术：T02、T03、T10。

### US-04 建立第二个项目并复用同事

**作为同一团队的使用者，我希望另一个项目复用团队能力，但不混入第一个项目的历史。**

新群说“沿用客户门户的团队，建立内部后台”，创建独立项目、资料首页、工作与项目记忆；同事的模型配置复用，不每群重新设置。结果明确“团队沿用，项目资料和历史独立”。两个项目可关联同一仓库，Agent 组织各自执行位置，不要求用户分配 worktree。

“参考 A 的验收清单”在可访问范围内建立带来源的引用或 B 的明确派生版本，不复制 A 全部聊天和记忆。来源不可访问时告知缺失，请提供可用来源，不绕过访问范围。

异常：同仓库不意味着复用同一可写 checkout 或 native session；共享目标分支存在并发改动时团队协调集成。单个项目故障不暂停其他项目；全局模型变更的影响另按 US-22 显示。

验收：UAT-09、10。技术：T02、T05、T08。

### US-05 维护固定入口和群绑定

**作为群成员，我希望一直从群顶部找到当前项目，而不是翻历史找最新上传。**

普通群默认建立一个“项目”文档 Tab，指向固定首页；发导航消息并 Pin。群顶部置顶是另一个能力：空位／已明确授权由系统维护时使用，不能因为 Pin 成功就宣称顶部置顶成功，也不能启动时盲目覆盖人工置顶。资料增长后按需增加“资料”“成果”文档或 URL Tab。

系统只能维护自己登记的入口。人删除或重新排列入口后，不无限重建争夺位置；项目仍可通过导航消息和自然语言访问，提示一次“固定入口已移除”，提供恢复操作。群文件是飞书的消息资料聚合，不承诺由 API 自建这种 Tab，也不当项目资料数据库。

异常：不支持 Tab 的群类型、超过平台数量限制或入口调用失败，使用导航卡／Pin／普通链接，显示哪种入口实际成功。文档权限不可访问时给可修复提示，不能因为能发链接就称全群可读。主群换绑先展示目标和影响；原群入口标记迁移去向，历史仍可追溯，不把旧群直接复用成另一项目的当前上下文。

验收：UAT-11、12、49。技术：T03、T10、T12。

## 4. 群里的日常工作与人的注意力

### US-06 自然语言提出需求或直接问问题

**作为用户，我希望向负责人讲事情，系统自行区分需要持续推进的工作和普通答复。**

“这个设计为什么这样做”可以直接答复；“给门户加批量导出”形成工作项，负责人回复范围、承接同事和必要的下一动作，不要求填写任务表。任务摘要卡包含标题、责任同事、当前范围、状态、讨论话题及已有来源链接；验收描述按需求逐步补全。

缺少业务取舍时提一个带选项和建议的问题；可独立进行的调查继续。不能把默认猜测写成用户已确认要求。明确只是随口讨论时不启动代码修改。新群的独立 `/workspace` 等旧命令给出新入口说明，不执行旧 room handler；引用、代码块或文档里的 slash 保留为正文。

验收：UAT-13、14、43。技术：T03、T04、T11。

### US-07 负责人分工，专家直接交流并行工作

**作为发起人，我希望负责人把工作做下去，不需要我逐次唤醒或替同事转述。**

复杂需求由负责人创建相关工作与依赖、分配责任；简单任务可自行完成。专家可直接向另一专家提问、提交结果或请求评审。主群看到分工和关键变化，话题记录必要协作证据，不把所有内部消息都广播给人。

同一同事可以在多个明确工作流并行工作，负责人忙碌不阻止其他成员接收任务。角色等待依赖时保存进度并释放执行资源；回信到达后自动继续。容量不足只让执行等待，不拒绝登记任务。资源允许时独立工作必须真并行，不能把全团队固定串行化。

异常：依赖成环时拒绝这次关联并指出环；无人能处理的工作显示等待责任分配；同事暂不可用时保留工作，负责人可重分配。重复无进展交接合并成一个阻塞，负责人改变策略或请求必要决定，不无限互相 @。

验收：UAT-15—17。技术：T04、T05、T08。

### US-08 在工作过程中修改要求

**作为用户，我希望在原话题补充文字或截图，所有相关同事都按新要求推进。**

示例：“先只做 CSV，Excel 后面再做。”系统用当前话题／引用确定工作，保存要求修订，负责人简短说明保留项和后移项。相关执行收到变更；可以安全追加时继续本轮，不能安全追加时保存新要求并在边界重排。显示“要求已记录，正在同步给工程师”，收到应用证据后再称已采用。

新要求改变先前结果的适用性时，旧成果留存并标明针对旧要求；旧测试或验收不自动满足新版本。若 issue 是权威来源，外部更新待同步时明确标示，涉及冲突范围的实施先等权威状态核实。

异常：“把那个改一下”无法定位时给相关工作的简短选择；不按最后发言 Bot 或最近活跃项目猜。工作已完成后的新增要求形成关联后续工作，或者用户明确重新打开原工作；不改写历史交付记录。

验收：UAT-18、19、34。技术：T04、T06、T09。

### US-09 查看进展并直接询问专家

**作为用户，我希望知道谁在做什么，并能越过负责人直接讨论细节。**

“现在怎么样”“还有什么卡着”返回总体结论、最近实质进展、阻塞、接下来由谁处理和链接。工作入口可查看按状态分组的工作列表；无进展时如实说明，不能用反复“正在努力”冒充进度，也不编造完成百分比或截止时间。

话题里 @ 质量负责人可直接得到答复。若形成要求／决定，答复角色记录到相关工作并通知负责人；不是每次都等负责人转述或批准。纯 FYI 信息可已阅不回复。用户问某个角色状态时区分“忙着另一个项目”和具体其他项目内容，未共享的项目细节不外泄。

验收：UAT-20、21。技术：T03、T04、T11。

### US-10 用自然语言调节注意力与责任

**作为用户，我希望根据项目阶段增加自己的参与，或把一类决定交给负责人。**

| 输入 | 保存的约定 | 当前工作怎样变化 | 对用户的反馈 |
| --- | --- | --- | --- |
| “这阶段界面方案先给我看” | 当前项目／阶段、界面方案、此人参与点 | 对相关未完成方案建立人的查看／决定事项 | “界面方案实施前会先给你看；已完成方案保持原记录。” |
| “以后常规文案由你负责” | 此类决定委托负责人，持续有效 | 相关未处理人待办转交负责人，保留转交记录 | “常规文案由我决定；目前两项已接手。” |
| “过程别逐条报，给结果就行” | 合并过程汇报 | 不取消已有必须由人决定的事项 | “会合并进展；确实需要你决定时仍会单独找你。” |
| “这次我看，后面还是你来” | 当前事项的临时例外 | 只影响该事项，不改长期规则 | 明确这一次的对象与后续恢复的约定 |

规则优先按明确范围与来源处理：事项特例优于泛化约定；同一有权人的明确修订替换旧版本；不同人的相互冲突要求不靠“最后一句 wins”，先保留既有事实，由相关负责人提出需要的取舍。默认约定只在当前项目有效，跨项目必须明确。

用户可以问“现在我管哪些”“这条约定取消”，得到人可读清单与来源并修改。减少参与不自动关闭同事评审、测试或集成；增加参与也不要求发全部工具日志。

异常：转交前的旧决定卡不再接受原操作，应显示已转交和当前责任人；旧卡回复可作为新意见保存，不伪造“已人工批准”。变更只影响未完成工作，不自动撤销过去决定。涉及正在发生且不可撤回的动作，说明已发生事实和余下能调整部分。

验收：UAT-22—25。技术：T04、T09、T11。

### US-11 找到并处理真正需要我的事项

**作为用户，我希望一次看到需要我判断的事情，并在群里完成简单决定。**

“现在有哪些必须我处理”返回去重清单，每项有对象、需要我的原因、负责人建议、影响与最少必要证据。公开事项出现在项目首页；个人跨项目清单通过本人私聊展示，不写入共享首页。

点击决定卡可选择具体选项、提出修改、明确交给负责人。多项独立请求可批量查看，不能让一个“全部同意”跨越不同对象或未展示的版本。“这个可以”只有引用／话题可明确定位时作为决定；否则询问是哪一项。意见提交后立即反馈所采用对象、结果与下一责任人。

异常：资料版本已变化时显示“你看到的是旧版本”，给差异和当前入口，不能把对旧版的赞同当新版本批准。团队确实可以自己解决的阻塞由负责人吸收，不因为队列里有等待项就全转交给人。

验收：UAT-26、27。技术：T04、T09、T11。

### US-12 自动采用合适的工作方法

**作为用户，我希望团队具备计划、评审、集成和交接能力，但不用为每个项目配置死流程。**

内置计划与分工、同行评审、集成回归、交付、负责人汇总、资料记忆维护等方法。角色根据任务和项目现有规范按需采用；用户说“这个多找一个人看”“这里只要快速演示”会调整采用方式。常见小问答不用创建评审任务。

采用方法时关联版本和实际结果，不能因为加载了“测试方法”就显示测试通过。角色可以提出方法改进，但不能悄悄升级全团队规范。团队方法升级在新采用或明确安全边界生效；当前事项继续显示自己采用的版本。

异常：方法要求与用户本项指令不同，按明确有效指令调整并说明重要影响；方法所需角色不可用时负责人安排替代或说明阻塞，不伪称独立评审。方法内容不可读时保留当前已采用版本，不猜测最新步骤。

验收：UAT-28、29。技术：T09。

## 5. 成果、反馈与共享资料

### US-13 交付足够我判断的成果

**作为用户，我希望看到做成什么、可信依据和需要我做什么，而不必查看所有文件。**

交付消息按固定信息顺序组织：结论／成果 → 与上次的关键变化 → 实际验证及限制 → 当前需要人的动作（没有则明确无需处理）→ 必要链接。简短答复直接发消息；反复迭代的方案、报告和页面使用稳定资源；一次性下载可用附件，但原件和保留责任明确。

同事显式发布／登记成果并通知，不能靠总结里恰好出现文件名触发正式交付。已保存但未发出通知显示“成果已保存，通知待发送”；任务无需人的验收时可以完成并保留通知待发送，不伪称用户已经收到。若本项明确要求交付文件，缺少该文件就不能宣称交付完成。

异常：成果只在临时 worktree 时先持久化再称已交付；上传失败保留原文件和发布操作，可重试同一成果。普通演示或问答不强制写一份报告。旧自动上传可用于用户主动监督，不能承担本合同。群里的面向人答复显式发送，原生 final 不再重复广播；普通私聊保留逐轮回复，已经显式发送的同一结果只显示一次。`/sendfile` 临时分享不被强制升级成长期成果。

验收：UAT-30、31、32。技术：T07、T10、T11。

### US-14 针对成果反馈、检查与返工

**作为用户或评审同事，我希望我的意见准确指向所看的成果，修改后能看到变化。**

在交付话题、成果卡或已接入文档评论中提意见，记录对象、所见版本／观察时间、内容和作者；负责人／责任角色读取后说明处理结论。需要迭代时更新同一资源并保存版本关系；新交付展示变化与已处理／未处理意见。不能把“评论读过”当作“问题解决”。

按项目约定需要检查时，安排合适同事检查指定对象；检查可为固定 commit／文件版本，也可以明确标注时间和范围的当前页面走查。返工成果不继承旧版通过结论；检查者可以确认变化影响范围后复用明确仍有效的证据。

异常：评论事件遗漏通过查阅时补读恢复；锚点删除时保留原引用和意见，改挂当前对象时说明。不是所有飞书评论都能实时无损同步，入口应提供“同步反馈”或负责人读取操作。用户反馈未解决而发布新版本时给出处理说明，不通过反复换文件规避意见。

验收：UAT-33、34、35。技术：T04、T07、T10。

### US-15 完成代码集成，处理分歧

**作为项目使用者，我希望多个同事的成果组合后真正能用，具体开发流程沿用项目约定。**

采用代码评审／集成的项目中，实现者给具体变更，检查角色记录基于哪个版本的结论，指定集成人通过原生 Git／PR 处理组合、冲突与验证。负责人最终说明当前到本地修改、commit、PR、合入或部署哪一步，不把其中一步混称最终上线。

基线前移时集成人重新核对差异和受影响验证；同一仓库多个项目协调目标分支。Agent 自己操作分支与 worktree，人只在方向、真实资源选择或确实需要的冲突决策上参与。未提交演示也是有效交付形态，只要当前要求如此。

异常：人正在使用的脏目录不能被自动 reset／清理；冲突由角色先分析解决，业务取舍才请求人。外部 PR 已合并而本地回执丢失先核实，不再合一次。原生运行结束、issue 关闭、PR 合并、业务验收分别展示。

验收：UAT-36、37。技术：T05、T07、T08。

### US-16 原位维护资料，清楚区分权威来源

**作为用户，我希望说“补进需求说明”时更新原文，而不是又产生一个临时上传。**

默认采用下列分工，可由项目已有组织方式覆盖；一旦选定来源就明确记录，其他位置只引用／投影：

| 内容 | 推荐权威位置 | 交互规则 |
| --- | --- | --- |
| 团队方法、术语和标准 | 团队 Docx／既有 Wiki | 多项目引用原件；项目例外单独说明 |
| 产品背景、用户流程、阶段决定 | 项目 Docx | 更新同一文档，给修改摘要和稳定链接 |
| 工作项范围与业务状态 | 项目采用的 issue 或内部工作项 | 不再在表格维护一套可独立改写的状态 |
| 代码、代码审查、CI、合并 | repo／PR | 群展示真实链接与回执 |
| 随代码成立的技术契约、部署和仓库规范 | repo docs | 随代码版本更新；飞书预览标明来源版本 |
| 用例库、业务台账、资料索引 | Bitable | 标明人工列、系统列、外部事实投影列 |
| 计算、预算、比较矩阵 | Sheets | 明确输入、公式及输出范围，局部更新 |
| 原图、文件集、导出报告 | 持久文件／制品存储 | 稳定资料身份与版本；消息附件用于分发 |

用户可以直接贴已有文档链接或上传 PDF、图片、表格、文件，再说明“按这份做”或“把它归入项目资料”。系统先反馈收到的对象与读取状态，引用已可访问原件；附件先作为本次输入，明确成为工作依据或长期资料时登记持久资源并保存所需内容。单独上传且用途不明时保留待使用附件，不默认公开到其他范围或立即启动开发。过大、格式不支持、下载失败或解析不完整时给出具体缺口，可处理的内容继续，不能凭文件名假装读过全文。

第一次建立资料说明去向；后续按资源身份更新，不按同名标题猜文档。不自动生成 PRD、issue、表格、repo docs 四份相同正文。若人指定了已有文档，优先关联它。

异常：源不可用显示缺失原因；可用旧缓存必须标明版本与获取时间。换目录、换模型或清理 worktree不删除长期资料。对内容归属有歧义时询问原件，而不是盲目另建一份。

验收：UAT-38、39。技术：T10。

### US-17 与人共同编辑文档和表格

**作为资料作者，我希望 Agent 的更新保留我同时进行的修改，并能处理版本冲突。**

Agent 先读所需版本，更新相关块／字段／单元格，回读结果并记录变更摘要；人改的其他部分不覆盖。在线文档的草稿编辑是变化信号，不自动等于采用新任务要求。明确用户要求变更则按 US-08 同步。

当前资料链接始终打开当前原件；“看当时交付”打开明确版本或固定材料。需要严格复现时保存必要内容、范围和来源证据。Sheets／Bitable 跨页读取没有原子一致性保证时，只能标作某时间段采集的数据集；要求严格同版时先形成可核实基线，不能用多次读到一样就称原子快照。

异常：发现目标区域被人改动，提交差异与建议，重新读取后整合；平台不提供强条件写入时不承诺绝对无覆盖。重要人工编辑区默认以建议后采纳方式更新。多表部分写入显示每项成功／待处理，不用全局“成功”遮盖一半失败。对公式和人工列有破坏性的操作不当普通状态刷新执行。

验收：UAT-40、41、60。技术：T10。

### US-18 管理临时材料、长期资料和保留

**作为用户，我希望临时方案有稳定反馈位置，值得保留的成果不会随缓存清理消失。**

材料分别记录用途和保留责任：工作临时文件可清理；正在讨论／等待决定的材料保持可用；已声明交付的版本受引用保护；长期规范在原件持续维护。临时方案不必加入长期知识正文，但也不能在待审时按一天 TTL 删除。

“把这份沉淀成项目规范”更新明确长期资料并保留来源。“这份不用了”先结束相关讨论并归档引用；永久删除是明确动作，展示受影响资料／成果关系，不能等同于清理 Agent 临时目录。系统不管理全部本地散落文件，但所有对外交付必须进入登记和保留合同。

异常：临时源被清理时从已发布版本读取；未发布文件丢失如实说明并由责任角色恢复，不能凭摘要重造后声称原文件仍在。团队原件被项目引用，归档单个项目只结束该项目引用，不删除团队原件。

验收：UAT-32、44。技术：T07、T10、T12。

## 6. 记忆、单聊与精确控制

### US-19 指导同事并纠正记忆

**作为用户，我希望同事逐渐熟悉工作，又能看清它记住了什么、适用于哪里。**

本项反馈、本项目规范、团队通用规范、角色通用方法、个人偏好分别保存。系统对显式“记住”简短反馈范围与来源；一般执行经验由角色记为有来源的经验，不升级成用户命令。启动或重建会话先读简短恢复索引，需要细节时查资料。

“你为什么还按旧规范做”“忘掉这个偏好”可查来源、纠正／撤销记忆，并使后续查询和注入使用新版本。对正在运行且已经读到旧内容的会话，发送变更并按需要暂停或重建；不能宣称数据库删掉就让所有原生上下文立即遗忘。

异常：来源已更新的摘要标过期并重新读取；跨项目经验只有明确提炼并有适用条件时进入通用层。故障恢复不能只靠模型最后一条总结；任务事实、待办、资料和检查点共同恢复。

验收：UAT-42、45。技术：T06、T09。

### US-20 在单聊工作，并明确进入或退出项目

**作为用户，我希望私人对话携带持续记忆，同时可以请同事帮某个项目做事。**

私聊默认个人范围。开始新话题仍保留个人偏好与适用经验；无需为普通问答建项目。说“继续客户门户的导出”或选择项目后，回复／卡片显示“正在协助：客户门户”；存在多个同名项目时选择真实对象。说“回到我自己的事情”或点击“返回个人工作”，后续输入回个人范围，原项目已登记工作按既定状态继续。

进入项目不把私聊内容自动发群。“把这份结论发到客户门户”只分享明确内容和成果，反馈目标群／话题；不发布整段私人对话。私聊里对项目的明确工作指令可以进入项目任务，但保存私密来源，公开摘要仅包含执行所需内容；有保密意图时先在个人草案处理，公开前按具体分享意图执行。

异常：没有项目访问范围时不注入项目记忆；多用户私聊同一 Bot 的偏好不混用。离开私聊或切换当前查看的工作不杀后台任务。仅“帮我看看”不被解释为授权公开。

验收：UAT-46、47。技术：T02、T03、T06、T11。

### US-21 保留单聊命令，摆脱群内命令操作

**作为已有用户，我希望在私聊仍能精确控制运行；在群里只需组织工作。**

私聊保留当前适用命令、别名和菜单，映射到统一工作内核：

| 现有命令族 | 私聊目标语义 | 新群的对应方式 |
| --- | --- | --- |
| `/stop /steerall /compact` | 控制选定工作；按 backend 实际能力执行 | 明确对象的卡片停止／自然语言修改；自动维护上下文 |
| `/new /history /list /use /useall /detach /follow` | 新个人工作、历史和查看／明确接管；导航不改变后台任务 owner | 通过工作／话题导航，独立接管控件 |
| `/workspace` 及其 list/new/dir/git/worktree/detach 子命令 | 保留明确资源操作；已存在资源精确选择 | 建立／调整资源时选择；日常 Git 由 Agent 做 |
| `/mode /model /reasoning /access /plan /verbose /codexprofile /claudeprofile /opencodeprofile /mcpoauth` | 保留适用的模型、会话和管理设置；明确全局／当前工作范围 | 需要时调用选择控件；管理通常进入 Bot 私聊 |
| `/goal /autowhip /autocontinue /review /bendtomywill` | 保留 backend 支持的本地会话控制和审查能力 | 协作／方法／持续执行由团队机制承接 |
| `/sendfile` | 主动发送选定文件，可登记成果；不自动当长期发布 | 显式交付或临时分享 |
| `/status /help /menu /admin /upgrade /debug /vscode-migrate` | 保留适用管理与诊断入口 | 工作状态与项目入口；系统管理不藏进群任务 |
| `/primary /coworkers` | 原本群专用，不新增私聊版本 | 新团队／负责人／成员用例替代 |
| `/cron` | 明确退役，不再运行旧计划 | 无旧 Cron 替代入口 |

44 个现有规格／43 个不同 canonical 命令及 backend 限制见[代码盘点](./feishu-agent-codebase-reuse-assessment.md#51-slash-command-盘点与去向)。不新增一个代码里不存在的 `/attach`；`patch` 等菜单键不当 Slash 命令宣传。

`/new` 在当前明确范围创建新的 WorkContext，默认是个人范围；已进入项目时保持项目范围，不清空长期记忆；“重建当前原生会话”是同一工作下的维护操作。`/use` 等导航切换查看／后续输入目标，不自动取得控制权。`/detach` 移除当前查看关联；尚在运行的工作保留，若涉及释放人工控制则走明确交接。

为保留旧私聊 `/stop` 体验，在个人工作中它停止当前工作并撤销尚未派发的用户排队输入；这些输入保留撤销记录。私聊已选择项目工作时，`/stop` 采用项目暂停语义，项目 inbox 全部保留，不能撤销其他成员的要求。同事回信和成果不被当成待发用户消息删除。群“暂停”只关闭工作准入并停止执行，未处理信息保留，继续时使用。

验收：UAT-43、48、50。技术：T03、T06、T11、T12。

### US-22 精确选择模型、资源与持续执行控制

**作为用户，我希望精确选模型和真实工作目录，系统说明改变会影响哪些工作。**

同一同事的 backend/model/profile/reasoning 统一管理，私聊选择时展示“影响该同事后续工作”，列出尚在旧配置执行的事项；已明确指定有效选择直接采用。当前已冻结执行不被静默换参数，新配置在实际安全边界生效；每个工作可查看正在使用的配置。切 backend 用持久工作上下文重建，不假装转移 native session ID。

access/plan 等已有会话级设置保持当前工作范围；控制宿主的 headless／编辑器模式归当前工作，不再全 Bot 切换所有项目。选择已有目录展示宿主、路径、仓库信息；Agent 可建议但不代替人选未知资源。改绑定先停止／交接相关旧执行，再在新位置恢复，长期资料和 ProjectID 不变。

会话 Goal 位于工作详情的“持续执行”，不是项目目标栏。当前仅 Codex headless 有原生 Goal 接口；Claude 使用相同任务事实与调度连续性，不展示虚构 Goal 支持。Goal 结束不意味着任务验收，等待／暂停时不能由原生 Goal 偷偷重启工作。

异常：新模型连接失败保留目标配置和明确失败状态，由人选择恢复旧配置或修复；不默默换便宜模型。目录丢失转恢复流程，不能擅自选另一个同名目录。用户已明确要求切换时不增加无意义确认，但显示正在等待旧执行停止的事实。

验收：UAT-51、52。技术：T05、T06、T08、T09。

## 7. 中断、恢复、接管与生命周期

### US-23 暂停、继续和取消明确的工作

**作为用户，我希望随时制止团队，即使负责人正在忙或模型故障。**

任务卡“暂停”作用于所示工作及本次选择包含的子工作；项目控制卡“暂停项目”作用于本项目全部自动执行。点击即持久关闭新执行准入，然后发送中断并核实；反馈逐步为“已受理”“正在停止”“已暂停”。子工作独立服务别的任务时显示范围，不随意连带取消共享依赖。

“继续”仅恢复原明确范围，读取未处理输入、当前约定和检查点；项目恢复不会取消用户单独设置的任务暂停。“取消”结束该项工作和它专属的未开始子工作，保存成果与历史；共享依赖保留并调整需求方。取消是终态，新的工作请求形成新事项／明确重开关系，迟到消息不得自动复活。

紧急停止入口是确定性卡片操作，不排在模型队列后。自然语言“都停一下”在当前项目可明确时执行该项目暂停，不扩展到其他项目；有歧义且在私聊跨项目时展示范围选择。

异常：中断超时或失联显示“停止状态待核查”，仍禁新执行，不因超时释放相冲突的写占用。已发生的外部副作用不自动回滚；需撤销时让责任角色在明确范围核查处理。

验收：UAT-50、53、54。技术：T04、T05、T06。

### US-24 故障后自动恢复而不重复工作

**作为用户，我希望重启、网络异常或模型故障不会让我重新讲一遍，也不会重复发文档或改代码。**

系统区分消息已收、执行已开始、结果已保存、外部通知待确认。服务重启后读取未完成工作，核实原生执行和外部操作，再在未暂停的范围继续；必要时重建会话并载入检查点和当前资料。没有待办的群不因重启全部唤醒。

短暂错误自动退避恢复，只有影响实质进度或需要人处理时合并通知。显示“正在恢复”“等待宿主上线”或“外部结果待核查”；不用每次重试刷屏。失败原因相同、没有新证据时不反复让模型重试整轮。

异常：无法证明旧进程已停止时不启动第二个写进程；发送成功但回执丢失先查消息映射，不把同一要求重新派发。没有足够原生历史／操作证据时由恢复角色检查现场，再决定继续；无法判断的不可逆副作用只请求缺失的判断，不伪称自动恢复成功。

验收：UAT-55、56、57。技术：T04、T05、T06、T12。

### US-25 人工接管、处理原生请求和归还工作

**作为用户，我希望必要时亲自操作原生会话，但不与后台 Agent 同时争用。**

查看记录不夺取控制；“接管这项工作”显示对象，关闭自动派发、等待／中断当前执行，取得控制后再进入编辑器／桌面操作。期间消息继续进入待办。归还时显示人留下的改动、未处理输入和可用检查点，系统核对后恢复。用户切到其他查看窗口不等于归还。

原生工具授权／输入请求走独立请求卡，显示请求归属、要执行的具体操作和有效选择；它不等同业务方案验收。授权结果按原生响应回执显示；人可以先停止整个工作。产品参与约定不擅自伪造原生审批回答，既有明确执行策略可按其规则使用。

异常：接管失联不自动回收后启动第二个 writer，先核实控制权；旧请求在 native session 更换后失效，不能拿旧卡批准新请求。卡片发送失败时请求仍存在于工作详情和适用私聊入口，无展示 surface 不意味着丢弃请求。

验收：UAT-48、58。技术：T05、T06、T11。

### US-26 更换同事、负责人或执行资源

**作为用户，我希望团队调整后已有工作能清楚交接。**

“让质量负责人接手这个检查”保存新责任与代次，旧执行停止／交接后将要求、已有成果、未处理意见和阻塞传给接手者。普通角色退出项目，先列出受影响工作并由负责人安排；新任务不再分给退出者。负责人更换时交接待决定事项、参与约定和总体工作记录，群入口显示新负责人。

移除 Bot 的平台事件只说明通信能力变化，不等于删除角色与项目。非负责人被移除后其工作转等待并通知负责人；负责人被移除且没有既定接任人时关闭新的自主委派，已有独立且已授权工作可继续，待协调事项保留并通过可用入口提示。所有项目 Bot／输出入口均失效时项目进入暂停待恢复，防止团队长期在失联群后面继续自主扩展工作。

异常：旧角色迟到结果保留为原尝试结果，不覆盖新责任人的状态；移除角色不删除其已交付资料。换资源按 US-22 处理，不能通过改群名／改目录标签让旧任务静默变成新项目。

验收：UAT-49、59。技术：T02、T04、T05、T12。

### US-27 归档、重新打开和解除群关联

**作为用户，我希望结束项目后停止执行，资料仍可查；以后也能明确恢复。**

“归档这个项目”停止新任务和自主执行、核实在途操作、保存检查点和未完成工作清单，完成后首页变为只读索引并显示归档状态。资料原件按原本编辑权限保留，系统停止自动改写；归档不是永久删除。重新打开保留同一 ProjectID，检查成员、资料与资源，再由用户明确继续哪些未完成工作，不把旧队列全部立即重放。

解除主群关联时若有替代入口，迁移导航并保留历史；没有替代入口则暂停项目并给操作者私聊／管理入口说明。把旧群用于新项目必须明确建新项目并换绑定，旧消息和卡片仍属于旧项目。

异常：原生运行未停时显示归档中，不提前标全停；远端文档不可访问不阻止保存内部归档事实，但列明资料缺口。永久删除需要独立明确对象和范围，不能复用归档按钮或临时清理。

验收：UAT-49、54、59。技术：T02、T05、T10、T12。

### US-28 从现有产品迁移

**作为已有用户，我希望现有接入和个人工作可继续，新群体验可以彻底换成团队模式。**

迁移前列出现有 Bot、个人工作、群与目录关联、未完成执行和 Cron 计划。Bot 凭据与统一模型配置保留；个人上下文、可核实的原生会话和已有资料关联导入，不能把旧对话自动加工成用户已确认记忆。群选择转为项目时核对负责人、资源和资料入口，旧 primary/coworkers/room 控制停止生效。

迁移窗口中保存新输入但暂停该迁移单元的派发；切换后只有新运行层写入执行事实。旧卡显示已迁移和新入口。旧 Cron 停止，计划／历史可读，不自动转成新任务或新定时器。旧上传缓存不是永久资料，明确被继续使用的材料先转持久资料，再允许旧清理运行。

异常：无法确认身份或正在运行的 session 时隔离该单元，显示原因，不影响其他已完成迁移。切换前失败可回到原权威；切换后有新工作只能前滚恢复，不用旧快照覆盖。用户看见迁移结果和待处理缺口，不要求理解 schema。

验收：UAT-44、46、60。技术：T12。

### US-29 正确处理消息编辑、撤回和过期入口

**作为用户，我希望修正聊天内容时，团队能区分更正、撤回和已经执行的工作。**

编辑／撤回事件能够被取得时记录来源变化并通知相关工作；历史补读用于核对，不把旧消息重放成新任务。撤回已经被执行的需求消息不等于取消任务或回滚副作用，系统提示“原消息已撤回，关联工作仍在进行”，提供暂停／取消入口；明确的新指令按 US-08／23 生效。

平台没有可靠编辑／撤回事件时不承诺自动即时感知，用户可直接发“上一条作废／改为……”；产品据此处理当前工作。话题根消息被删时保留内部工作，必要时建立替代讨论锚点并告诉用户原关联，不把回复投到任意最近消息。

验收：UAT-19、27、57。技术：T03、T04、T11。

### US-30 明确当前能力与不可用状态

**作为用户，我希望得到可执行的路径，而不是一个看起来成功、实际上无效的按钮。**

选择器和命令帮助按 backend／当前控制模式提供实际能力：Claude 尚未接通的原生 compact／Goal 不显示成已支持；目标连续性通过受控检查点与重建实现。运行维护和改功能不是一回事，不能用“某 backend 不支持原生接口”放弃项目级记忆与恢复。

外部 API 暂不可用时保留意图、说明范围并提供对应替代：无 Wiki 建空间能力用已有 Wiki 或 Drive／Docx；无 Tab 用导航卡／Pin／链接；源没有强版本一致性时明确观察数据集而非冒充原子版本。权限启用属部署工作，不在设计上删减可接入能力。

验收：UAT-12、41、52、60。技术：T06、T10、T11。

测试数据至少包含：两个项目、同一组跨项目角色、两个私聊用户、同仓库不同工作位置、一个共享团队资料源；分别运行 Codex 和 Claude。以下“假定／当／则”为 Given／When／Then；每项保存输入、可见反馈、状态前后和对应持久／外部证据。不能只靠一张卡片截图判通过。

| 编号 | 假定与操作 | 应观察到的结果 |
| --- | --- | --- |
| UAT-01 | 已接入 Bot，用户描述职责并选模型 | 角色稳定 ID、职责版本、真实配置保存；不要求长提示词 |

| UAT-27 | 点旧决定卡／对旧成果说可以 | 显示当前状态或差异；不批准未展示的新对象／版本 |
| UAT-28 | 简单答复与复杂改动采用方法 | 适度选择；没有强制流水线；实际证据与方法采用分别记录 |
| UAT-29 | 降低人参与、同行检查仍必要 | 同事继续承担检查，不能因“人不用看”而删除检查 |
| UAT-30 | 文件任务未发布；另测群显式答复及私聊有／无显式发送 | 文件未发布不称已交付；群 final 不重复广播；私聊无显式发送仍有回复、有则只发一次；问答／临时 sendfile 不强制长期发布 |
| UAT-31 | 成果保存成功、群消息发送失败 | 稳定成果可查，通知待发送可恢复；不重复发布版本 |
| UAT-32 | 清理临时 worktree／24h 预览缓存 | 已交付及待决策材料仍可读，不依赖被清理源 |
| UAT-33 | 对版本 V1 提意见，作者发布 V2 | 意见来源、处理结论与版本关系保留；读过不等于解决 |
| UAT-34 | 要求或成果版本改变 | 旧评审保留但不自动满足新要求；复用证据有明确适用范围 |
| UAT-35 | 文档评论通知遗漏／锚点丢失 | 通过读取补齐；保留原意见，不虚构实时全量同步 |
| UAT-36 | 并行改动需集成且目标 ref 前移 | Agent 处理冲突和适用验证；展示真正完成的交付层级 |
| UAT-37 | 人的 checkout 有未提交修改 | 无平台自动 reset/clean；旧操作未知先核实，不重放合并 |
| UAT-38 | 上传／引用需求资料，再多次“补进需求说明”；另测读取失败 | 读取状态真实，采纳附件持久化；更新同 Resource／链接，不增生副本；解析不完整不冒充已读全文 |
| UAT-39 | issue／PR／repo docs 与飞书资料共同使用 | 每种事实来源明确；投影不能反向伪造关闭／合并 |
| UAT-40 | 人与 Agent 同时改目标段落／单元格 | 局部更新、冲突提示／建议及回读；不宣称 API 强 CAS |
| UAT-41 | 要求严格复现表格，但读源不具同版保证 | 明确不满足条件，先形成可核实基线；观察数据集标签准确 |
| UAT-42 | 纠正／删除记忆并换模型 | 新查询／注入使用新版本；运行中旧内容被明确处理；个人隔离保留 |
| UAT-43 | 群旧 Slash、正文代码 Slash、私聊别名 | 分别指引新入口、保持正文、执行适用私聊用例；无旧群状态写入 |
| UAT-44 | 旧缓存转长期资料，再归档一个引用项目 | 持久源不受旧清理影响；团队原件和其他引用保留 |
| UAT-45 | 源规范更新而记忆摘要仍旧 | 标过期并读新源，不让隐藏摘要长期胜过原件 |
| UAT-46 | 两用户私聊同 Bot，迁移／重新连接 | 各自资料与记忆独立；不能用最后 Actor 或 gateway 槽位认人 |
| UAT-47 | 私聊进入项目后 `/new`，再返回个人并明确分享摘要 | new 保持当前项目 scope 与长期记忆、旧工作继续；返回个人后范围正确；仅分享指定内容，不公开私聊历史 |
| UAT-48 | 切 `/use`、`/detach` 或旁观编辑器 | 不改变后台 owner；接管须明确交接，原生请求仍可处理 |
| UAT-49 | 删除入口／移除 Bot／换群 | 不争夺人工入口；按剩余协调和输出能力降级或暂停，历史可查 |
| UAT-50 | 群暂停、个人工作 `/stop`、私聊选中项目 `/stop` 分别执行 | 群及项目工作保留 inbox，不丢其他成员要求；个人工作撤销未派发用户队列，保留撤销证据和同事回信 |
| UAT-51 | 全局改模型时多个工作运行／排队 | 目标配置和各执行实际配置可见；冻结项不静默变更；失败不擅自换模型 |
| UAT-52 | Codex/Claude 分别维护上下文与 Goal | 真实能力不同但工作持续性成立；Goal 不替代任务完成或越过暂停 |
| UAT-53 | 模型忙碌／失联时按暂停 | 无需模型处理先禁准入；实际停下与待核查分别显示 |
| UAT-54 | 取消／归档后迟到结果、再次重启 | 结果保留、不复活工作；实际未停不显示已归档全停 |
| UAT-55 | 入站登记、启动、结束各窗口崩溃 | 已接单不丢；未知执行先核查；不重复启动写进程 |
| UAT-56 | 外部写成功但未落回执即崩溃 | 对账或显式未知，不盲目重复发送／建文档／执行脚本 |
| UAT-57 | 多 Bot 同收、内部回显、话题根丢失 | 一次业务输入；回显不重复委派；明确重锚，不乱投最近话题 |
| UAT-58 | 接管断线或旧 native request 卡迟到 | 控制权先核实；新会话不能收到旧批准；停止入口仍可用 |
| UAT-59 | 换负责人／归档再打开 | 工作与参与约定交接；旧 owner 不能覆盖；重开不全部盲续跑 |
| UAT-60 | 迁移切换／外部多步骤写入部分失败 | 显示分步事实；切换后唯一权威、无旧 Cron；不能总体成功掩盖局部失败 |

## 9. 本轮默认设计决定与实现边界

本轮无需增加用户决策门，采用以下可调整但已足够实施的默认值：普通群一个主项目；默认“项目”文档 Tab 加导航 Pin；顶部置顶只在明确可维护时使用；普通私聊默认个人范围；项目归档暂停执行但保留资料；方法库按情境采用；材料待处理／已交付引用保护不设隐式短 TTL。品牌命名、卡片视觉细节、具体并发数与预算可在实现时配置，不改变上述合同。

项目需要人批准到什么程度、用不用 issue、交付到哪一步不是产品待拍板项，按项目阶段约定。部署时需要接通的真实平台与 runtime 能力是实现责任，不能拿“尚未验证”替代实现；若底层确实没有某种原语，必须采用本文已经规定的等价产品路径，并展示真实限制。
