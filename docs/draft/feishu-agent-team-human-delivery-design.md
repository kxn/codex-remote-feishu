# 人与 Agent 的交付约定：Raft 源码依据与飞书适配

> Type: `draft`
> Updated: `2026-11-21`
> Summary: 核查 Raft 的消息、附件、Artifact 与反馈机制，提出显式交付、人的注意力入口及资料存放规范。

## 1. 范围与结论

新团队模式中，人监督方向、关键决定和交付，不逐轮检查所有 Agent 产物。旧的“从模型总结识别文件并预上传”服务于逐次监督场景，有其用途；它不应继续承担可靠交付或长期资料登记的责任。

本轮重新读取 Raft 公开源码，Git tree 的 main 仍指向 `5214e34e726ed715f455e78c96fa521791ef2de3`。以下区分常驻提示、按需工作指南、代码约束和本项目建议；未运行 Raft 服务，不把文档中的工作习惯误写成所有任务必经的状态机。

结论：借鉴 Raft 的**明确发布、稳定成果身份、版本反馈和负责人筛选信息**。它没有用统一目录规则解决所有文件管理问题。我们针对飞书补充可执行的交付与存放约定，但不扩展成平台代管 Agent 所有文件／Git 操作。

本文件的飞书适配是待讨论设计，尚未实现。底层资料接口与限制见 [共享资料设计](./feishu-agent-team-materials-design.md)，完整体验见 [产品设计](./feishu-agent-team-product-design.md)。

## 2. Raft 已经怎样做

### 2.1 输出给人是明确动作

[常驻提示构造](https://github.com/botiverse/raft-source/blob/5214e34e726ed715f455e78c96fa521791ef2de3/packages/daemon/src/drivers/systemPrompt.ts) 要求通过 Raft CLI 沟通；底层 Agent 的普通输出不能当作对话送达。实际运行处理将原生文本记入轨迹，turn 结束也不据此发布文件或替 Agent 发群消息，见 [AgentProcessManager](https://github.com/botiverse/raft-source/blob/5214e34e726ed715f455e78c96fa521791ef2de3/packages/daemon/src/agentProcessManager.ts)。

Codex 的特定输出场景会记录 communication gap（有文字而没有工具调用／发送尝试）；检测并不覆盖所有漏交付，也不阻止 turn 结束或自动补发。`agentVisibleDeliveryLedger` 记录的是送给模型的输入与读取新鲜度，不是给人的成果交付账本。不能因变量名有 delivery 就把它当成发布保证。

### 2.2 消息、附件、Artifact 分开

[Artifacts 常驻能力说明](https://github.com/botiverse/raft-source/blob/5214e34e726ed715f455e78c96fa521791ef2de3/packages/shared/src/apps/artifacts/guide.ts) 与 [Agent 手册](https://github.com/botiverse/raft-source/blob/5214e34e726ed715f455e78c96fa521791ef2de3/manual/agent-knowledge/artifact.md) 给出的默认选择：

- 简短、不需要迭代的内容直接发消息。
- 一次性下载／分发用附件；改变内容需要新的附件上传。
- 需要反复修改、收反馈或稳定链接的页面、报告、方案、图表及文件集使用 Artifact。

因此 Artifact 也可以只是本次决策用的短期方案，不必先证明它是长期知识。一次性附件也不意味着它的业务价值只能保留一天。**使用方式与保存期限不是同一个分类轴。**

### 2.3 稳定身份与反馈闭环有实际实现

[CLI push](https://github.com/botiverse/raft-source/blob/5214e34e726ed715f455e78c96fa521791ef2de3/packages/cli/src/commands/artifact/publish.ts) 发布目录；[本地目录状态](https://github.com/botiverse/raft-source/blob/5214e34e726ed715f455e78c96fa521791ef2de3/packages/cli/src/commands/artifact/_dir.ts) 通过 `.raft-artifact.json` 保存 Artifact 身份、基线版本及文件 hash。后续 push 更新同一 Artifact，版本不可变；无变化不制造新版本，删除文件要明确指定。默认跳过隐藏／工具目录不是完备的敏感信息审查，也不证明所有工作目录已被规范管理。

[服务端发布](https://github.com/botiverse/raft-source/blob/5214e34e726ed715f455e78c96fa521791ef2de3/packages/server/src/apps/artifacts/publish.ts) 对同文件基线变化、未读相关反馈等有拒绝／暂缓逻辑。发布者需先读到反馈，再据此继续；“模型读过”仍不等于它正确解决了意见。

[Artifacts 首页](https://github.com/botiverse/raft-source/blob/5214e34e726ed715f455e78c96fa521791ef2de3/packages/server/src/apps/artifacts/webDashboard.ts) 另有待回应提及、关注动态与最近使用等视图；其中 waiting 基于未读评论提及，不是完整的项目决策／验收队列。

发布内容和在对话中通知是两个动作。Agent 发布后取得链接，再发消息说明该看什么；单纯 push 不自动在目标对话发布一条消息。界面可查看历史、批注和文件，频道 Files 也能找回成果。不能把 API 的发布成功当成人已经知道，更不能当作已读／验收。

[save](https://github.com/botiverse/raft-source/blob/5214e34e726ed715f455e78c96fa521791ef2de3/packages/server/src/apps/artifacts/save.ts) 是将现有附件保存成 Artifact，并非“草稿等待人工批准”阶段。人 review 和评论是独立能力；没有证据表明 Artifact 发布一律要经人批准。

### 2.4 人的注意力由负责人整理

[负责人汇总指南](https://github.com/botiverse/raft-source/blob/5214e34e726ed715f455e78c96fa521791ef2de3/manual/recipes/pattern/coordinator-synthesis.md) 要求按工作全貌汇总状态、责任、证据入口与待决定事项，去重并指出人先看什么。它不要求转发全部轨迹，也不让负责人包办所有实现。

[交付证据指南](https://github.com/botiverse/raft-source/blob/5214e34e726ed715f455e78c96fa521791ef2de3/manual/recipes/technique/proof-of-work-receipts.md) 主张提供足以核查的最小证据，普通低影响工作只需简短状态和链接。[验收位置指南](https://github.com/botiverse/raft-source/blob/5214e34e726ed715f455e78c96fa521791ef2de3/manual/recipes/technique/acceptance-surface.md) 要求核查人实际会看的页面／文件／结果，而非只有源文件或内部测试通过。

这些是按需 recipes，而非全由服务端强制。借鉴其选择性汇总，不连带复用提醒／Cron 或要求每次生成复杂报告。

### 2.5 Raft 没有替我们解决的事

其常驻工作区规则明确允许灵活组织，主要规定 MEMORY.md 作为恢复索引、notes 保存详细知识，没有强制所有角色使用统一的临时／长期／对外交付目录树。Artifact 的受管版本与本地工作目录是两种机制。

[页面检查](https://github.com/botiverse/raft-source/blob/5214e34e726ed715f455e78c96fa521791ef2de3/packages/server/src/apps/artifacts/checks.ts) 在 HTML 发布后进行，既不覆盖所有文件类型，也不是业务验收门槛。[上传块清理](https://github.com/botiverse/raft-source/blob/5214e34e726ed715f455e78c96fa521791ef2de3/packages/server/src/apps/artifacts/blobs.ts#L376) 针对无版本引用的数据，已发布版本仍引用的内容不会因该上传 TTL 被删除。

另有范围有限的硬门禁：[资源创建任务](https://github.com/botiverse/raft-source/blob/5214e34e726ed715f455e78c96fa521791ef2de3/packages/server/src/services/taskService.ts#L4206) 若要求 resource receipt，缺少回执及回收责任／到期跟进时不能设为 done。这不能泛化为所有文件任务都必须发布 Artifact，更不是用户已收到交付的证明。

因此不能直接声称“换成 Raft 提示词，模型就不会乱放文件、忘记发布或漏看反馈”。我们仍需定义预期交付、持久引用和清理边界，并诚实承认系统不能自动判断所有未登记文件的语义价值。

## 3. 飞书适配：提示、链接与固定入口各有职责

用户提出的三种方式组合使用：

1. **工作约定**告诉 Agent 何时交付、怎样选择材料和需要谁处理；不靠最终回复中的文件名触发正式发布。
2. **消息／卡片＋稳定链接**承载一次具体交付；在群内就能理解结论、变化和所需动作，不必先读完整文档。
3. **固定项目入口**汇总人需要处理的事项、当前成果与长期资料；它是同一事实的索引／视图，不再复制一套正文。

不设置一个把所有“给人看的东西”永久堆在一起的目录。面向人的临时评审材料、已经交付的成果、长期知识各有状态；人不需要在文件堆里猜哪一份需要自己处理。

## 4. 人默认看什么

项目资料首页增加三块固定视图：

| 视图 | 展示内容 | 退出／更新方式 |
| --- | --- | --- |
| 待我处理 | 需要此人决定、反馈或验收的事项，附简短背景、推荐意见与准确对象 | 处理后退出待办，保留决定和对应成果版本 |
| 当前成果 | 已交付内容及最新有效版本，最近变化、验证结论和关联事项 | 新交付取代当前入口，旧版本仍从历史可查 |
| 项目资料 | 持续维护的产品说明、规范、业务表和 repo 文档入口 | 原位更新、归档或解除引用 |

“待我处理”具有接收人，群内不公开个人私聊待办；多人关注同一事项也不意味着都必须批准。普通项目公共首页可以展示公开的待决定事项及负责人，个人入口只筛选与本人有关的事项。

人默认接收重要阻塞、明确决策请求、约定的评审及成果交付。细节证据放在任务话题／资料引用中，执行轨迹留在诊断入口。负责人合并重复反馈，专家在自己负责的话题直接答复；普通问答照常直接回复，不先建文档或交付清单。

对外交付固定回答：做成了什么、与上次相比变了什么、验证到什么程度、是否需要人做什么，并附准确成果入口。没有待决定事项时明确无需操作，不把每项进展都包装成审批。

## 5. 文件与内容按两条轴管理

### 5.1 用途与保存责任

| 类别 | 示例 | 存放与保留规则 |
| --- | --- | --- |
| 内部过程材料 | 草算、测试中间文件、调试输出 | 任务 scratch，默认不通知人；无活动执行／恢复／成果引用后才可按策略清理 |
| 待讨论／待评审材料 | 供选方案、原型、截图对比、临时分析 | 发布为有版本的评审资料，关联话题；未处理或仍支撑决定时保留，不因“临时”自动删 |
| 正式交付及证据 | 导出文件、报告、PR／commit、验收截图 | 持久登记并固定本次版本；依项目保留策略归档，不能仅留在本地 worktree／临时预览 |
| 持续维护的知识 | PRD、规范、架构文档、台账 | 使用既定权威载体长期维护，纳入项目／团队资料索引 |

另记面向谁：内部同事、指定评审者、用户、项目全员。发布给人并不自动提升为团队长期规范；长期知识也不需要每次变化都推送给所有人。

默认保留所有已发布评审／交付版本及其未解除引用，关闭后允许按项目既定保留策略归档／清理；尚未设置策略时不沿用临时预览 TTL 删除。归档不是删除。明确的删除／隐私要求按资料合同处理，不用“永久保留”阻止用户删除。

### 5.2 固定存放约定，保持原件唯一

- 系统提供带 scope/context 的工作路径说明：scratch 用于可丢弃中间文件，working 用于尚未发布草稿，cache 用于已登记资料的本地读取副本。这是辅助资料目录，不改写用户仓库结构，也不介入 Agent 的 worktree 组织。
- 需要长期维护的原件写入其权威位置：repo docs 随 Git 提交，飞书文档／表格写原生对象；持久附件与验收版本进入独立资料存储。
- 草稿可以先在本地生成，但被称为“已保存／已交付”之前必须完成正式登记和持久化。不能靠把文件放进名为 final 的目录获得这个状态。
- 本地 working／cache 不成为第二份权威正文；记录 ResourceID、源版本和待发布修改。工作区清理不会清除云端原件与持久版本。
- 未分类文件默认视为内部材料，**不自动上传，也不因未分类就自动删除**。在任务收尾时由责任 Agent 分类；需要交付但尚未登记的材料不能被一段总结替代。

不扫描并上传 Agent 工作目录全部文件。系统只能检查声明的交付对象与路径边界；“所有重要文件都已发现”仍需要责任 Agent 的内容判断和任务验收。

## 6. 显式交付与运行层约束

### 6.1 预期交付

需要成果的任务在承接时记录交付类型、受众、必要产物及验收方式。普通解释可约定为一条答复，代码修改可约定 PR＋验证结论，不要求所有任务额外生成报告。约定随明确需求修订，不允许执行者为通过完成检查偷偷改为“无需交付”。

专家给负责人／其他专家的中间交接同样有成果引用，但不默认通知用户。负责人检查整体交付是否符合用户要求，再形成面向人的摘要与必要链接；不要求它手动搬运每个文件。

### 6.2 发布结果与送达分开

新增 Delivery 记录：scope/task、受众、意图（告知／决策／评审／交付）、简要结论、需人动作、ArtifactVersion／ResourceVersion／PR／commit 引用、关联话题、保留类别和操作回执。单聊使用个人 scope，普通消息不强迫存在 Task。

Agent 通过显式 CLI 业务操作准备／提交，命令名由统一 registry 定义；不另外预加载大套工具。服务端检查必需成果、版本、允许范围与持久保存结果，再将可发送的交付和 outbox 在同一事务中关联。外部保存是前置 operation，不能放进数据库事务伪造原子提交。

阶段区分：材料准备中、可交付、通知待发送、通知已送达、已被新交付替代；人的决定／验收另存。发布成功不代表发送成功，发送成功不代表已读，已读不代表验收。重试复用 Delivery／operation 身份，避免每次创建新文档或新待办。

对约定必须交付的任务，缺少持久成果时不能标记交付完成；有成果但通知失败显示待送达。任务是否最终关闭仍按其验收方式、issue 权威和授权决定，不强迫每个成果都等人审批。人的暂停可随时停止执行，不被交付完整性检查阻挡。

### 6.3 提示词与硬检查的分工

常驻规则只需说明：内部过程不全量外发；重要交付走明确发布；人先看结论和所需动作；重复修改更新同一资源；交付前读相关反馈；长期成果不只存临时目录。详细发布、保留与命令帮助按需读取。

领域层强制身份、必需引用、保存成功、版本与任务关联、去重及 outbox 状态。负责人／评审角色判断内容是否足够、证据是否支持结论、哪些材料值得让人看。结构化记录不能替代这些内容判断，也不能保证从未登记的遗漏一定被发现。

飞书无法照搬 Raft 自有 Artifact 的全部评论锚点和发布门禁。能读到的原生文档评论与群反馈关联到资源／任务／版本；发布前读取已接收的反馈 revision 并核对当前源版本，无法判断评论对应哪个版本时明确待核对。普通通知不强制等人发表评论。

## 7. 旧机制保留到哪里

旧自动预览可留作现有逐次监督／用户主动展开的辅助能力；新团队模式默认不通过扫描 native final 自动批量上传文件。与新交付重复时只展示已登记的同一链接，不新增副本，也不改变交付状态。

保留下载、图片显示、附件传输和按需预览组件。旧缓存与清理器继续只处理自己的临时资源，不接管正式成果；若出现跨范围、重复上传或误删风险，移除冲突路径，不为保留旧体验扩大新合同。

这既不要求删光原有能力，也不把“原功能存在”当成新团队必经流程。单聊可按用户需要保留方便的即时预览，但正式交付与持久资料使用同一套规则。

## 8. 验收与关联文档

- 模型最终总结没有提文件，但已通过 Delivery 发布的成果仍能在话题和固定入口找到。
- 只在总结写“文件已完成”，没有保存和登记，不会把约定的文件交付标记完成。
- 内部产生很多中间文件，人只收到应看的结论和必要材料；不同专家同一阻塞只产生一项人的待办。
- 同一方案多轮反馈仍使用同一资源；评审对象固定版本，新版本不会继承旧验收。
- 临时决策材料在等待人处理时不被清理；长期成果不会随 worktree 或预览缓存删除。
- 发布成功后断网，恢复继续发送同一交付；群消息成功不等于用户验收。
- 普通对话不强制写文档；已有 repo 规范和 Agent 自主管理 Git 不被辅助目录约定替换。
